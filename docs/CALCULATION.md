อธิบายทีละชั้น — และมีจุดหนึ่งต้องแก้ก่อน: เลขสองตัวนั้นไม่ใช่ตอนหาความสัมพันธ์ มันคือตอน ค้นหา/recall (หน้า /search และ /meowtam recall) ป้ายสองคำนั้นมาจาก server.py:2119 ที่แปลชื่อ stage ของ retrieval เป็นภาษาคน ส่วนตอนหา ความสัมพันธ์ (resolves / blocked_by) ไม่ใช้เลขพวกนี้เลย มันใช้คำ cue + กฎระดับบรรทัด ไม่มีคะแนน

1 · "คำตรงกัน 0.81" มาจากไหน
ตัวเลขนี้คือ BM25 ซึ่งเป็นสูตรมาตรฐานของการให้คะแนน "คำที่ตรงกันจริง" — lexical.py คิดสามอย่างต่อหนึ่งคำที่ query กับข้อความนั้นใช้ร่วมกัน:

คำนี้หายากแค่ไหน (IDF) — REVERAPP-183 โผล่ 3 ครั้งในคลัง 1,301 ข้อความ → คำนี้แทบชี้ขาด · ครับ โผล่ทุกที่ → เกือบไม่ได้แต้ม สูตรคือ log(1 + (จำนวนข้อความทั้งหมด − ที่มีคำนี้ + 0.5) / (ที่มีคำนี้ + 0.5))
พูดซ้ำกี่ครั้ง — ซ้ำช่วยเพิ่ม แต่อิ่มตัว (k1 = 1.5) พูดคำเดิม 10 ครั้งไม่ได้แต้ม 10 เท่าของครั้งเดียว ไม่งั้นคนสแปมคำเดียวก็ชนะ
ข้อความยาวหรือสั้น — ยาวกว่าถูกหักลง (b = 0.75) เพราะโพสต์ 500 ตัวอักษรมีโอกาสมีคำตรงโดยบังเอิญมากกว่าข้อความสั้น
ก่อนนับ ต้อง ตัดคำ ก่อน เพราะไทยไม่เว้นวรรค — ใช้พจนานุกรม PyThaiNLP (newmm) ตัดฝั่งไทย และตัดฝั่งอังกฤษแบบรู้จัก identifier (getUserProfile, REV-1421 ไม่ถูกหักเป็นชิ้น) จุดสำคัญที่ทำให้กลไกนี้มีค่า: ถ้าไม่มีคำร่วมกันเลย คะแนนเป็น 0.000 สนิท ไม่ใช่ 0.3 ไม่ใช่ 0.1 — นี่คือเหตุผลที่ระบบกล้าตอบว่า "ไม่เจอ"

2 · "ความหมายใกล้กัน 0.90" มาจากไหน
อันนี้คือ cosine ระหว่างเวกเตอร์ โมเดล BAAI/bge-m3 แปลงข้อความหนึ่งเป็นตัวเลข 1,024 ตัว (เหมือนพิกัดในห้องที่มี 1,024 มิติ) ประโยคที่ความหมายใกล้กันจะชี้ไปทางเดียวกัน แล้ววัดว่า "สองลูกศรนี้ทำมุมกันกี่องศา" — ทางเดียวกันเป๊ะ = 1.00

ที่มันมีประโยชน์คือ ไม่ต้องใช้คำเดียวกัน พิมพ์ "รอ API sorting" แล้วเจอข้อความที่เขียนว่า "ยังไปต่อไม่ได้ ต้องรอฝั่ง backend" ได้ และข้ามภาษาได้ด้วย เพราะโมเดลวางไทยกับอังกฤษไว้ในห้องเดียวกัน

ข้อควรระวังที่เขียนไว้ในเอกสารเลย: cosine ไม่ใช่เปอร์เซ็นต์ ไม่ใช่ความมั่นใจ 0.90 ไม่ได้แปลว่า "มั่นใจ 90%" มันเทียบกันเองได้เท่านั้น

3 · แล้ว 0.81 / 0.90 ที่โชว์บนแถว หมายความว่าอะไรจริง ๆ
ตรงนี้คือส่วนที่คนเข้าใจผิดง่ายที่สุด เลขบนแต่ละแถวผลลัพธ์ถูก บีบให้อยู่ 0–1 เทียบกันเองในลิสต์นั้น (retrieve.py:337 — min-max)

ตัวที่ดีที่สุดในลิสต์ = 1.00 · ตัวที่แย่ที่สุดในลิสต์ = 0.00 · ที่เหลือเฉลี่ยอยู่ระหว่างกลาง

ดังนั้น 0.81 = "แถวนี้อยู่ที่ 81% ของช่วงระหว่างแถวที่แย่สุดกับดีสุดในลิสต์นี้ ในแง่คำที่ตรงกัน" ไม่ใช่ 81% ของอะไรที่เป็นสัมบูรณ์ ถ้าไปค้นอีก query หนึ่ง เลข 0.81 ตัวนั้นเทียบกับอันนี้ไม่ได้เลย มันตอบได้แค่ "ในผลชุดนี้ อะไรดันแถวนี้ขึ้นมา — คำตรง หรือความหมาย"

ส่วนเลขสองตัว บนหัวหน้า (ไม่ใช่บนแถว) เป็นของคนละชนิด: นั่นคือค่าดิบไม่ผ่านการบีบ (relevance.lexical = BM25 ดิบ, relevance.dense = cosine ดิบ — retrieve.py:236) และเป็นตัวที่ใช้ตัดสินว่า "มีเรื่องนี้อยู่ในคลังจริงไหม" ต้องผ่าน ทั้งคู่: BM25 > 0 และ cosine ≥ 0.45 นี่คือด่านที่ทำให้ตอบว่าไม่เจอได้

และ ลำดับ ของแถวไม่ได้มาจากการเฉลี่ยเลขสองตัวนี้ — มันมาจาก RRF ที่รวม อันดับ ของแต่ละสัญญาณ ไม่ใช่รวมคะแนน (เพราะสองสัญญาณสเกลคนละเรื่อง: BM25 วิ่ง 0 ถึง 25 ส่วน cosine วิ่ง 0.4 ถึง 0.9 ถ้าเฉลี่ยดิบ ๆ BM25 จะกลืนอีกฝั่งทั้งหมด)

4 · ตอนแบ่งกลุ่ม — "เรื่องเดียวกันจริงไหม"
ตรงนี้เปลี่ยนวิธีคิดทั้งหมด ไม่ใช่การตั้งเลขเกณฑ์ต่อคู่ เพราะคำถาม "ในช่องนี้มีเรื่องอะไรอยู่บ้าง" เป็นคำถามกับทั้งกองพร้อมกัน ไม่ใช่คำถามทีละคู่ วิธีที่ใช้คือ ทำเป็นกราฟ แล้วหาก้อน (graph.py)

ขั้นที่ 1 — ลากเส้นระหว่างข้อความที่อาจเกี่ยวกัน สองทางเท่านั้น:

เพื่อนบ้าน 6 อันดับแรกตามความหมาย และต้อง เลือกกันเอง — A จะต่อกับ B ได้ต้องอยู่ใน 6 อันดับแรกของกันและกัน ข้อดีคือมันฆ่า "ข้อความอมตะ" อย่าง มีอัปเดตมั้ย ที่ใกล้ทุกเรื่องในโลก ตัวนั้นถูกทุกคนเลือกก็จริง แต่ตัวมันเลือกใครไม่ได้ครบ เส้นจึงไม่เกิด
อยู่เธรด Slack เดียวกัน = ลากเส้นเสมอ ไม่สนใจว่าคำจะเหมือนกันไหม เพราะเธรดเดียวกันเป็นข้อเท็จจริง ไม่ใช่การเดา (แต่ ห้ามทำแบบนี้กับที่ประชุม เพราะประชุมเดียวมีสิบเรื่อง ถ้าลากทุกคู่ ประชุมทั้งอันจะยุบเป็นก้อนเดียว)

ขั้นที่ 3 — Louvain หาก้อน พูดแบบไม่มีศัพท์: มันลองหยิบข้อความหนึ่งไปใส่ในกลุ่มของเพื่อนบ้าน ถ้าย้ายแล้ว "เส้นข้างในกลุ่มแน่นขึ้นเทียบกับเส้นที่พาดออกไปข้างนอก" ก็เก็บการย้ายนั้นไว้ แล้วทำวนไปจนย้ายอะไรก็ไม่ดีขึ้นอีก ข้อดีคือมันตัดสินเองว่าควรมีกี่กลุ่ม ไม่ต้องบอกล่วงหน้าเหมือน k-means (และ seed คงที่ ผลจึงซ้ำได้เป๊ะทุกครั้ง)

มีปุ่มเดียวคือ resolution = 4.0 ยิ่งสูงยิ่งแบ่งละเอียด และเลขนี้มาจากการวัดสองทาง ไม่ใช่ความรู้สึก — ที่ 1.0 ก้อนใหญ่สุดมี 132 ข้อความและก้อนหนึ่งปนทิกเก็ตต่างกัน 19 ใบ (นั่นคือ "แชนเนล" ไม่ใช่ "งาน") ที่ 4.0 เหลือ 50 ข้อความและ 7 ใบ · ที่น่าสนใจคือการผ่างานจริงออกเป็นเสี่ยงก็ลดลงด้วย (31% → 9%) เพราะที่ค่าต่ำ ก้อนดูดข้อความตามช่องและเวลาแทนที่จะตามเรื่อง — ไม่มี tradeoff ให้เลือก 1.0 แย่กว่าทั้งสองทาง ต้นทุนที่ต้องพูดคือความครอบคลุมลด 90% → 85% เพราะก้อนเดี่ยวหลุดเกณฑ์ min_messages (digest.py:437) — พวกนั้นยังค้นเจอ แค่ไม่ถูกเรียกว่า "งาน"

ขั้นที่ 4 — ตั้งชื่อก้อน ไม่มีโมเดลเขียน ชื่อคือ anchor ที่สมาชิกในก้อนใช้ร่วมกันอย่างมีเอกลักษณ์ที่สุด (เช่น uat, event mobile preview) ถ้าไม่มีของร่วมกันเลยก็เขียนตรง ๆ ว่า (no shared anchor) แล้วไปใช้ประโยคสรุปเป็นหัวข้อแทน

จุดที่ควรจำเวลาถูกถาม: ความหมายใกล้กันใช้หา "อะไรเกี่ยวกับอะไร" ส่วนสถานะติด/เสร็จไม่ได้มาจากเลขพวกนี้เลย — มันมาจาก cue ในบรรทัดที่คนพิมพ์จริง แล้วชี้กลับไปยังบรรทัดนั้นเป็นหลักฐานได้
