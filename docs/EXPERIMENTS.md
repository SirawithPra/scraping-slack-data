## 3. เทียบโมเดลสำเร็จรูป — ตัวที่เลือกอยู่ในนี้

วัดบน `real_all.json` (1,102 record) · held-out 24 thread ที่โมเดลไม่เคยเห็น

**accuracy** = triplet accuracy: ให้ข้อความหนึ่ง โมเดลบอกได้ไหมว่าเพื่อนใน thread เดียวกัน
ใกล้กว่าคนแปลกหน้าจากอีก thread (50% = เดาสุ่ม)
**ขยะ** = cosine สูงสุดที่ query ไร้ความหมาย 5 แบบทำได้ · **label ต่ำสุด** = cosine ต่ำสุดที่
ชื่องานจริง 12 อันจาก corpus เองทำได้ (การันตีว่ามีของให้แมตช์)

|---|---|---|---|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` | 59.4% | 0.918 | 0.475 | 128 | ตัวที่ใช้อยู่เดิม — อ่อนสุด |
| `paraphrase-multilingual-mpnet-base-v2` | 63.1% | 0.925 | 0.367 | 128 | แม่นดี แต่ขยะได้สูงสุด + context สั้น |

| **`BAAI/bge-m3`** | **63.7%** | **0.731** | 0.501 | **8192** | **เลือกตัวนี้** — ชนะทั้ง accuracy และขยะ |

**ทำไมเลือก `bge-m3`:** แม่นที่สุด (+4.3 จุดจากตัวเดิม), ขยะได้คะแนนต่ำสุดในกลุ่ม

## 5. Relevance gate — เปลี่ยน "กลไก" ไม่ใช่ "เลข"

gate เดิมถาม "cosine ของ record ที่ใกล้สุด สูงกว่า 0.45 ไหม" **กลไกนี้ผิดตั้งแต่ต้น**
ไม่ใช่โมเดลไม่ดี: `max cosine` เหนือ N เอกสารสูงขึ้นตาม N สำหรับ query อะไรก็ตาม
มี 1,102 เอกสาร ยังไงก็มีอันที่ดูคล้าย **ทดสอบ 5 โมเดล ไม่มีตัวไหนหา floor ที่แยกได้**

| กลไก | ขยะถูกกรอง | query จริงที่เสียไป |
|---|---|---|
| `cosine ≥ floor` (เดิม) | **0/5** | 0/12 |
| z-score — top hit โดดจากกลุ่มไหม | ยังทับกัน (margin −0.83 ถึง −0.93) | — |
| **`BM25 > 0` และ `cosine ≥ 0.50`** | **4/5** | **0/12** |

**ทำไม BM25 ชนะ:** ขยะไม่มีคำตรงกับ corpus เลย → ได้ **0.000 สนิท 4 จาก 5 ตัว**
ขณะที่ cosine หาอะไรคล้ายได้เสมอ ส่วน dense ยังต้องมีอยู่ เพื่อจับ query จริงที่ใช้คำต่างจาก corpus

**ตัวที่ยังหลุด:** `ๆๆๆ ฯฯฯ ฤฤฤ ฅฅฅ` — ๆ กับ ฯ เป็นอักขระไทยจริงที่มีใน corpus จึงมีคำตรงกันจริง
ไม่ใช่ bug ของกลไก แต่เป็นขอบเขตของมัน

## 6. ขนาด corpus ไม่ใช่ตัวแปรที่คิด

เคยเขียนไว้ว่า "corpus ยิ่งเล็ก ขยะยิ่งได้คะแนนสูง" **ผิด** วัดโดยสุ่มย่อยจาก corpus เดียวกัน:

| record | 25 | 50 | 100 | 200 | 400 | 936 |
|---|---|---|---|---|---|---|
| ขยะสูงสุด | 0.870 | 0.911 | 0.913 | 0.911 | 0.892 | 0.918 |

แบนและไม่เป็นเส้นตรง แต่ corpus **ต่างเนื้อหา** ที่ขนาดใกล้กันขยับเยอะ (0.581 / 0.767 / 0.918)
→ **เนื้อหากำหนด ไม่ใช่ขนาด** floor จึงเป็นคุณสมบัติของ corpus คู่กับโมเดล ต้องวัดที่หน้างาน

## 7. `0 blocked` บนข้อมูลจริง — cue ไม่ตรงภาษาทีม

digest บน `real_all.json` ได้ **37 active · 19 resolved · 0 blocked** ทั้งที่ "อะไรติด" คือฟีเจอร์หลัก

| cue ที่ระบบใช้ | เจอใน 936 ข้อความจริง |
|---|---|
| `ยังรอ` `ต้องรอ` `รออยู่` `ติดที่` `ยังไม่มา` `ยังทำไม่ได้` `blocked` `depends on` | **0 ทั้งหมด** |
| `waiting for` | 2 |
| คำที่ทีมใช้จริงแต่ไม่อยู่ในลิสต์: `pending` | 15 |
| `ค้าง` | 4 |

**กับดักสองอันที่ห้ามเติมมั่ว:**

1. **`รอ` เดี่ยวเจอ 92 ครั้ง แต่เกือบทั้งหมดผิด** — ภาษาไทยไม่มีเว้นวรรค `รอ` อยู่ใน
   "ร**อบ**" "ก**รอก**" "ห**รอ**" เช่นเดียวกับ `ติด` ที่อยู่ใน "ติดต่อ" "ติดตั้ง" "ติดตาม"
   **ทางแก้ที่ถูกคือตัดคำด้วย pythainlp แล้วแมตช์ระดับ token** — `รอบนี้` → `[รอบ, นี้]` ไม่มี token `รอ`
   แต่ `ยังรอ api อยู่` → `[ยัง, รอ, api, อยู่]` มี
2. **`blocker` 14 จาก 22 ครั้งมาจาก template standup** ที่ขึ้นหัวว่า "Any blockers?"
   เติมเป็น cue จะ fire ทุกโพสต์ standup

**สิ่งที่ระบบทำถูก:** มันรายงาน 0 ตรง ๆ **ไม่ได้แต่งงานติดขึ้นมา** ให้ดูดี

### 7.1 ปิดคำถามนี้แล้ว — คอขวดคือ "ระดับของสัญญาณ" ไม่ใช่ลิสต์คำ และไม่ใช่การจับกลุ่ม

ไล่ตัดผู้ต้องสงสัยทีละตัวด้วยการวัด:

| สงสัยว่า | วัดแล้วได้ |
|---|---|
| การจับกลุ่มยุบ blocker เข้าด้วยกัน | **ไม่ใช่** — blocked = 2 เท่ากันทุกค่า resolution ตั้งแต่ 1.0 ถึง 6.0 (ดู §7.6) |
| กลไกแมตช์คำไทยผิด | **ผิดจริง และแก้แล้ว** — เคยเป็น substring ซึ่งพลาดทั้งสองทาง (ดูล่าง) แต่ผลลัพธ์ปลายทางเท่าเดิม |
| ลิสต์คำไม่ครบ | **ครบไม่ได้ด้วยกลไกปัจจุบัน** ← คำตอบจริง |

**กลไกแมตช์: แก้แล้ว** docstring ของตัวแมตช์เขียนเองว่า *"Thai cues stay substring searches"*
ซึ่งจริงเรื่องภาษาไทยแต่ผิดในฐานะข้อสรุป และพลาดสองทางพร้อมกันจนบังกันเอง —
substring จับเกิน (`รอ` ใน `รอบ`/`กรอก`/`หรอ`) ขณะที่การแมตช์ token เดี่ยวจับขาด เพราะ cue ไทย
ส่วนใหญ่เป็นหลายพยางค์ที่ตัวตัดคำแยกออก (`ไม่ได้` → `[ไม่, ได้]`) จึงยิงไม่ได้เลย
**ทางที่ถูกคือตัดคำทั้งสองฝั่งแล้วหาลำดับ token ต่อเนื่อง** ตอนนี้ทำแล้ว

**แต่คำตอบจริงคือ `pending`** ซึ่ง §7 ชี้ไว้ว่าโผล่ 15 ครั้ง ลองเพิ่มเป็น cue แล้ววัด:

- blocked ขึ้นจาก 2 เป็น **3**
- **แต่หลักฐานของอันใหม่คือโพสต์ `"Sprint 3 is officially end *RECAP*"`** ซึ่งเป็นสรุปสปรินต์
  ไม่ใช่การบอกว่าใครติด มันเพียงมีคำ `pending` อยู่ข้างในโพสต์ยาว ๆ
- **จึงถอนออก** — ระบบที่อ้างสรุปสปรินต์เป็นหลักฐานว่ามีคนติด น่าเชื่อถือ*น้อยลง* ไม่ใช่มากขึ้น

วัดต่อว่าทำไมมันพลาด:

| | ข้อความที่มี `pending` | ข้อความทั่วไป |
|---|---|---|
| ความยาว median | **529 ตัวอักษร** | 46 |
| เป็นโพสต์หลายบรรทัด (≥4 บรรทัด) | **14 / 15** | — |

## 7.8 cue ระดับ**บรรทัด** — ปิดข้อค้างจาก §7.1 ที่ฝั่ง relation

§7.1 สรุปว่าคอขวดคือระดับของสัญญาณ และแก้ให้ฝั่ง blocker แล้ว (`ingest/blockers.py` อ่านทีละบรรทัด)
**ฝั่ง relation ไม่ได้แก้ และแก้ไม่ได้ด้วย** เพราะ `analysis_text` — ฟิลด์ที่ docstring สั่งให้ cue matching
อ่าน — ยุบ whitespace ทุกชนิดรวม newline ด้วย `re.sub(r"\s+", " ", ...)` วัดแล้ว: **โพสต์ 201 อัน
มี ≥4 บรรทัดใน `.text` แต่ `analysis_text` เห็นเป็นบรรทัดเดียวทั้ง 201 อัน**

เพิ่ม `quoted.asserted_lines()` — ตัด fence/quote/strike/inline-code แบบเดิมเป๊ะ แต่เก็บขอบบรรทัดไว้
และนิยาม `analysis_text = " ".join(asserted_lines(...))` ยืนยันแล้วว่าให้ผล**เหมือนเดิมทุกไบต์**
บน 1,517 record (0 mismatch) จึงไม่มี caller เดิมเปลี่ยนพฤติกรรม

**กฎที่เพิ่ม** cue ที่อยู่ใต้บรรทัดแรกของโพสต์ต้องมีอะไรผูกบรรทัดนั้นกับข้อความอีกฝั่ง — anchor ร่วม

| `reverapp-110` | 0.2% | 1 | **ถูก** — เปิดการ์ดบั๊กแล้วอีกฝั่งบอก `fixed bug [REVERAPP-110, REVERAPP-111]` |

`api` เป็น anchor เพราะ pattern `acronym` แต่ใน corpus นี้มันเป็นคำสามัญ การแชร์ `api`
จึงแทบไม่ใช่หลักฐาน — เป็นช่องเดียวที่โพสต์ daily ยังเล็ดลอดด่านได้

**ทำไมยังไม่แก้** ผิด 2 จาก 447 relation = 0.4% ของผลลัพธ์ กฎที่จะแก้คือ "anchor ต้องหาไม่ค่อยเจอ
ใน corpus" ซึ่งช่วงที่ใช้ได้กว้างสบาย (0.7% เก็บ, 3.0% ตัด) และเข้ากับหลักที่โปรเจกต์นี้ใช้อยู่แล้ว

## 7.10 `pending` ที่ตามหลังคำว่าเสร็จ — แก้แบบแคบ และบอกว่าหลักฐานบางแค่ไหน

`"P'Mos - Done all API pending + support"` ถูกอ่านเป็น blocker เพราะมีคำ `pending`
แต่ประโยคหมายความว่า *API ที่ค้างอยู่ทำเสร็จหมดแล้ว* บรรทัดเดียวนี้ดัน work item ขนาด
26 ข้อความขึ้นรายการ blocked ด้วยตัวเอง — 1 ใน 5 ของรายการ blocked ตอนนั้น

กฎที่เพิ่ม: **คำบอกความเสร็จที่มาก่อน cue การรอ ตัดบรรทัดนั้นออก เว้นแต่มีคำพลิกประโยคคั่นอยู่**
(`but`, `however`, `แต่`)

**หลักฐานบางมาก และเขียนไว้ตรง ๆ** ทั้ง corpus มีแค่ 2 บรรทัดที่เข้าเงื่อนไข อันละทิศ:

| บรรทัด | ควรเป็น | กฎ "cue แรกชนะ" เฉย ๆ |
|---|---|---|
| `P'Mos - Done all API pending + support` | ไม่ใช่ blocker | ✓ ถูก |
| `ฝั่ง API event ผมต่อเสร็จแล้วครับ **แต่** Pending p'choke prepare api อีกตัวนึงอยู่` | **เป็น blocker จริง** | ✗ **จะทำของจริงหาย** |

คำว่า `แต่` เป็นตัวพลิกความหมายทั้งประโยค ถ้าไม่มีข้อยกเว้นนี้ กฎจะแลกของปลอม 1 อันกับของจริง 1 อัน
ซึ่งไม่คุ้ม — จึงยึดทั้งสองทิศไว้ใน `tests/test_blocker_lines.py` แทนที่จะฝากไว้กับการอ่าน docstring
ในอนาคต และข้อยกเว้นตั้งใจให้ยาวแค่ 3 คำ ไม่ใช่โมเดล negation ทั่วไป
ผลลัพธ์: blocker line 29 → 28 บรรทัด และ `c278acd` ยัง blocked แต่ย้ายไปอ้างหลักฐานจริง
(`"Pedning api event"`) วันที่ติดขยับ 10 ส.ค. → 6 ส.ค.

## 7.11 วัด cue ระดับบรรทัดใหม่ — `รอ` ยังไม่ผ่าน แต่คนละเหตุผลกับ §7.1

พบตอนจำลอง demo ว่าบรรทัด `Zac - รอ api ของ event audit log อยู่ ยังทำต่อไม่ได้` **ไม่ถูกอ่านว่าเป็น
blocker เลย** ตามไปดูพบว่าลิสต์ระดับ**บรรทัด** (`blockers.LINE_CUES`) ขาดคำที่ลิสต์ระดับ**ข้อความ**
(`relations` `blocked_by`) มีอยู่ 5 คำ: `depends on`, `can't until`, `cannot until`, `still need`, `รอ api`
(ทางกลับกัน `pending` อยู่ในลิสต์บรรทัดและจงใจไม่อยู่ในลิสต์ข้อความ — บรรทัดเล็กพอจะระบุที่มาได้ โพสต์ทั้งโพสต์ไม่พอ
อันนั้นมีเอกสารอธิบายไว้ ส่วน 5 คำนี้ไม่มีอะไรอธิบาย)

วัดทั้ง 5 คำบน corpus จริง: **เพิ่ม 0 บรรทัดทุกคำ** ช่องนี้จึงมองไม่เห็นในข้อมูลวันนี้ โน้ตที่แต่งขึ้นมาทดสอบ
เป็นสิ่งเดียวที่เปิดมันออก

**ที่น่าสนใจกว่าคือ `รอ` เปล่า ๆ** §7.1 ปฏิเสธไปเพราะ `text.find` เจอมันอยู่ข้างใน `รอบ` `กรอก` `หรอ`
จน hit 92 ข้อความ **แต่กลไกนั้นไม่มีอยู่แล้ว** — `thai_offset` ตัดคำสองฝั่งแล้วหาลำดับ token ต่อเนื่อง
`รอบนี้` เป็น `[รอบ, นี้]` ซึ่งไม่มี token `รอ` อยู่ ข้อสรุปเก่าจึงอาจเป็นผลข้างเคียงของกลไกเก่า วัดใหม่:

| cue | เพิ่มบรรทัด | ตัดสิน |
|---|---|---|
| `รอ` | 13 | **ไม่ผ่าน ~70%** |
| `ยังไม่ได้` | 8 | **ไม่ผ่าน** — เกือบทั้งหมดคือ "ยังไม่เริ่ม" ไม่ใช่ "ติด" (`fe mobile ผมยังไม่ได้ดู`) |
| `ยังทำต่อไม่ได้` | 1 | **ผ่าน 1/1 — เพิ่มแล้ว** |

`รอ` ไม่ผ่าน **แต่ไม่ใช่เพราะจับเกินในคำอย่างที่ §7.1 เขียน** ตอนนี้มันจับคำถูกแล้ว แต่ยังผิดสามแบบที่ไม่มี
ลิสต์คำไหนแก้ได้:

- **ประโยคปฏิเสธ** — `ใช่ครับ จะแก้ให้ในสปรินต์นี้ ไม่ต้องรออะไร` คือ *ไม่ต้องรอ*
- **UI copy ที่กำลังสั่งทำ** — `รอการยืนยันการจองจากเจ้าหน้าที่ผ่าน LINE Official Account ก่อนเข้าใช้บริการ`
- **การรอที่ไม่ใช่งาน** — `รอแลกตั๋วหนังดีกว่านะ`, `wด้ แค่รอมายมาเฟิม`

ส่วนที่ผ่าน 8–9 บรรทัดเป็น blocker จริงและชัด (`P'Jah - QA vehicle data รอตรวจ warranty พี่โชค`,
`แทตส่งอัพเดตตัว pop up ขึ้น store แล้วค่ะพี่แชมป์รอ approve`) — ถ้าจะเอา `รอ` ต้องมีตัวจัดการปฏิเสธก่อน
ไม่ใช่เติมคำเข้าลิสต์ **บันทึกไว้เพื่อไม่ให้ใครสืบทอดเหตุผลเก่าที่ไม่จริงอีกแล้ว**

`ยังทำต่อไม่ได้` ที่เพิ่มเข้าไปคือ `ยังทำไม่ได้` ที่มีคำแทรกกลาง ตัวตัดคำแยกเป็น `[ยัง, ทำ, ต่อ, ไม่, ได้]`
ลำดับ token ของคำเดิมจึงไปไม่ถึง blocker line รวม 28 → **29** บรรทัด

## 10. ค้างไว้: gate ยังหลุด query ภาษาจริงที่ไม่มีเรื่องนั้นใน corpus

พบตอนสาธิตให้ผู้ใช้ดู ไม่ใช่ตอนวัด — ซึ่งบอกอะไรอยู่

`lexical > 0` กรอง**ขยะ**ได้ (ตามที่วัดใน §5) แต่กรอง **query ภาษาจริงที่ไม่มีเรื่องนั้น**
ไม่ได้ ตัวอย่าง: `แผนการตลาดไตรมาสหน้าที่สิงคโปร์` ได้ bm25 = 9.66 จึงผ่านประตู
เพราะ pythainlp ตัด `ไตรมาสหน้าที่` ได้ token `หน้าที่` ซึ่งไปแมตช์ข้อความสั้นในคลัง
ที่มีคำว่า `หน้าที่` อยู่ (ข้อความยาวไม่ถึงสิบคำ) และ BM25 ให้แต้มสูงกับเอกสารสั้น
**คำสามัญคำเดียวก็ผ่าน**
ผลที่โชว์กลับมาไม่มีคำตรงกับ query เลย (`terms = []`)

**ตัวที่ลองแล้วยังไม่พอ** — coverage แบบ "คำนี้มีใน corpus ไหม" ได้ 1.00 เกือบทุก query
เพราะคำไทยเกือบทุกคำโผล่ที่ไหนที่หนึ่งใน 936 ข้อความ

**ตัวที่น่าจะใช่ ยังไม่ลง** — idf-weighted coverage **ภายในเอกสารเดียว** โดยให้คำที่
ไม่เคยเจอใน corpus มี idf **สูงสุด** ไม่ใช่ 0 (จุดนี้เป็นบั๊กใน metric รอบแรก: ให้ 0
ทำให้ query ที่คำส่วนใหญ่ไม่มีอยู่ ดูเหมือนครอบคลุมเต็ม)

| ชนิด | coverage |
|---|---|
| ขยะ 3 แบบ | 0.00 · 0.00 · 0.25 |
| เรื่องที่ไม่มีใน corpus 3 แบบ | 0.19 · 0.22 · 0.22 |
| เรื่องที่มีจริง 5 แบบ | 0.32 · 0.41 · 0.57 · 1.00 · 1.00 |

เกณฑ์ราว **0.28** จะกรองได้ 6/6 และไม่เสีย query จริงเลย 5/5 — **margin เป็นบวกครั้งแรก**
ในบรรดากลไกที่ลองทั้งหมด (cosine floor, z-score, cross-encoder, lexical>0)

**ทำไมยังไม่ลง** 11 probe ที่ผู้เขียนเลือกเอง margin แค่ 0.07 และไม่มีชุด held-out
การตั้งเกณฑ์บนตัวอย่างที่ตัวเองเลือกคือสิ่งที่เอกสารนี้วิจารณ์ไว้ใน §5 เอง
ต้องมี probe ที่คนอื่นเขียน หรือ query จริงจาก log ก่อนจะเชื่อ
