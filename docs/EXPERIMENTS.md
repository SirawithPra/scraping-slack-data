# บันทึกการทดลอง — เทรนอะไรไป ตัวไหนไม่ดีเพราะอะไร และสุดท้ายเลือกอะไร

เอกสารนี้เก็บ **ทุกอย่างที่วัดจริง** ไม่ใช่ที่คิดว่าจะเป็น ทุกตัวเลขมีคำสั่งที่รันกำกับไว้
ตัวไหนแพ้ก็บอกว่าแพ้เพราะอะไร เพื่อให้กลับมาเทียบใหม่ได้โดยไม่ต้องเดาว่าตอนนั้นคิดอะไรอยู่

**ข้อสรุปบรรทัดเดียว:** เปลี่ยนไปใช้ `BAAI/bge-m3` และเปลี่ยนกลไก relevance gate จาก
"cosine สูงกว่าเลขคงที่" เป็น "ต้องมีคำตรงกัน **และ** ความหมายใกล้" — **โมเดลที่เทรนเองทั้งสองตัวไม่ผ่าน**

## 2. เทรนไปสองรอบ ทั้งสองรอบไม่ผ่าน

> **น้ำหนักของทั้งสองโมเดลถูกลบไปแล้ว** (18 ส.ค. 2569 · คืนพื้นที่ 932 MB)
> เก็บไฟล์ 932 MB ที่เอกสารระบุเองว่าห้าม ship ไว้ ไม่คุ้ม ตัวเลขในหัวข้อนี้จึง
> **ตรวจซ้ำได้แต่ต้องเทรนใหม่** — คำสั่งอยู่ใต้แต่ละหัวข้อย่อย ใช้เวลา ~3 นาทีต่อตัวบน CPU
> (ถ้าจะทำ อ่าน "บทเรียน" ท้ายข้อ 2.2 ก่อน: ควรเปลี่ยนฐานเป็น bge-m3 ไม่ใช่เทรนบน MiniLM ซ้ำ)

วิธีเทรนเหมือนกันทั้งคู่: `MultipleNegativesRankingLoss` บนคู่ข้อความที่อยู่ thread เดียวกัน
แบ่ง held-out **ตาม thread ไม่ใช่ตามข้อความ** (แบ่งตามข้อความจะทำให้ครึ่งบทสนทนาไปอยู่ทั้งสองฝั่ง)

### 2.1 `models/syn_finetuned` — เทรนจากข้อมูลสังเคราะห์

```bash
python3 -m tam.evaluation.finetune --records data/processed/syn.json --out models/syn_finetuned --epochs 2 --batch-size 32
```

| | |
|---|---|
| ฐาน | `paraphrase-multilingual-MiniLM-L12-v2` |
| ข้อมูล | 927 ข้อความ · 2,984 คู่ |
| ผลบน held-out ของข้อมูลจริง | **61.4%** |

**ไม่ผ่านเพราะ** ภาษาที่เทรนไม่ใช่ภาษาที่ทีมใช้จริง และมันทำให้ cosine พุ่งขึ้นทั้งกระดาน
ขยะได้ **0.971** บน corpus จริง สูงกว่า query จริงที่อ่อนสุด (0.718) — relevance gate ใช้ไม่ได้เลย

### 2.2 `models/real_finetuned` — เทรนจากข้อมูลจริง

```bash
python3 -m tam.evaluation.finetune --records data/processed/real_all.json --out models/real_finetuned --epochs 2 --batch-size 32
```

| | |
|---|---|
| ฐาน | `paraphrase-multilingual-MiniLM-L12-v2` |
| ข้อมูล | 936 ข้อความ · 2,661 คู่ → เทรน 2,311 / held-out 350 คู่ จาก 24 thread |
| เวลา | 152 วินาที บน CPU |
| loss | 5.151 → 2.839 |
| ผลบน held-out | **60.9%** (ฐาน 59.4% → ดีขึ้น 1.5 จุด) |

**ไม่ผ่านเพราะสามข้อ:**

1. **ดีขึ้นแค่ 1.5 จุดจากโมเดลฐาน** และ **แพ้ของสำเร็จรูป 3 ตัว** ที่ไม่ต้องเทรนเลย
   ตัว `finetune` เตือนไว้ตรงตัวว่า *"If it does not beat the base model, the corpus was too
   small — that is information, not a failure"* ซึ่งคือสิ่งที่เกิดขึ้น
2. **ทำให้ปัญหา anisotropy หนักขึ้น** cosine ทุกคู่พุ่ง (same-thread 0.760 vs other-thread 0.720
   ห่างกันแค่ 0.04) ขยะได้ **0.964** เป็นตัวที่แย่ที่สุดในบรรดาที่วัดทั้งหมด
3. **context ยัง 128 token** เพราะฐานเป็น MiniLM — 13.4% ของ record จริงถูกตัด (ดูข้อ 4)

**บทเรียน:** corpus ระดับ ~900 ข้อความ / 24 held-out thread เล็กเกินกว่าจะชนะโมเดลสำเร็จรูป
ถ้าจะกลับมาเทรนอีก ต้องได้ข้อมูลมากกว่านี้หลายเท่า (ช่องเดียวชน limit 200 ข้อความ = ยังมีของเก่ากว่าอีก)
และควรเปลี่ยน**ฐาน**เป็น bge-m3 ก่อนเทรน ไม่ใช่เทรนบน MiniLM ต่อ

## 3. เทียบโมเดลสำเร็จรูป — ตัวที่เลือกอยู่ในนี้

วัดบน `real_all.json` (1,102 record) · held-out 24 thread ที่โมเดลไม่เคยเห็น

**accuracy** = triplet accuracy: ให้ข้อความหนึ่ง โมเดลบอกได้ไหมว่าเพื่อนใน thread เดียวกัน
ใกล้กว่าคนแปลกหน้าจากอีก thread (50% = เดาสุ่ม)
**ขยะ** = cosine สูงสุดที่ query ไร้ความหมาย 5 แบบทำได้ · **label ต่ำสุด** = cosine ต่ำสุดที่
ชื่องานจริง 12 อันจาก corpus เองทำได้ (การันตีว่ามีของให้แมตช์)

| โมเดล | accuracy | ขยะ | label ต่ำสุด | context | สรุป |
|---|---|---|---|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` | 59.4% | 0.918 | 0.475 | 128 | ตัวที่ใช้อยู่เดิม — อ่อนสุด |
| `paraphrase-multilingual-mpnet-base-v2` | 63.1% | 0.925 | 0.367 | 128 | แม่นดี แต่ขยะได้สูงสุด + context สั้น |
| `intfloat/multilingual-e5-base` | 60.6% | 0.860 | 0.819 | 512 | กลาง ๆ ทุกด้าน |
| `intfloat/multilingual-e5-large` | 61.4% | 0.838 | 0.817 | 512 | ใหญ่กว่า e5-base แต่ดีขึ้นแค่ 0.8 จุด |
| **`BAAI/bge-m3`** | **63.7%** | **0.731** | 0.501 | **8192** | **เลือกตัวนี้** — ชนะทั้ง accuracy และขยะ |
| `models/syn_finetuned` | 61.4% | 0.971 | 0.718 | 128 | เทรนเอง — ขยะแย่ |
| `models/real_finetuned` | 60.9% | 0.964 | 0.817 | 128 | เทรนเอง — ขยะแย่สุด |

```bash
# ทำซ้ำได้ — ทุกโมเดลนี้ download ไว้ใน ~/.cache/huggingface แล้ว ไม่ต้องโหลดใหม่
python3 -m tam.evaluation.compare_models --catalog
```

**ทำไมเลือก `bge-m3`:** แม่นที่สุด (+4.3 จุดจากตัวเดิม), ขยะได้คะแนนต่ำสุดในกลุ่ม
(0.731 เทียบ 0.918) และ context 8192 แก้ปัญหาข้อ 4 ได้เลย
ข้อเสียคือ 568M พารามิเตอร์ = น้ำหนัก 2.1 GB บนดิสก์ และช้ากว่า MiniLM — รับได้เพราะมี embedding cache อยู่แล้ว

**ทำไมไม่เลือก `mpnet`:** accuracy ใกล้กัน (63.1 vs 63.7) แต่ขยะได้ **0.925** สูงสุดในตาราง
และ label ต่ำสุดแค่ 0.367 → ช่องว่างกว้างที่สุด = gate แย่ที่สุด

**ทำไมไม่เลือก `e5-large`:** ใหญ่กว่า e5-base เท่าตัวแต่ได้เพิ่ม 0.8 จุด ไม่คุ้ม

## 4. context 128 token คือปัญหาที่มองไม่เห็น

MiniLM และ mpnet ตัดข้อความที่ 128 word piece **แบบเงียบ ๆ**

| corpus | median | p90 | max | เกิน 128 | token ที่ทิ้ง |
|---|---|---|---|---|---|
| `combined.json` (42) | 45 | 136 | 521 | 12.8% | 740 |
| `real_all.json` (1102) | 20 | 175 | 1,459 | **13.4%** | **22,916** |

ข้อความส่วนใหญ่สั้น (median 20) แต่ที่ยาวคือ **thread record กับ standup template** ซึ่งเป็น
ตัวที่สำคัญต่อการจัดกลุ่มที่สุด — bge-m3 (8192) และ e5 (512) ไม่มีปัญหานี้

## 5. Relevance gate — เปลี่ยน "กลไก" ไม่ใช่ "เลข"

gate เดิมถาม "cosine ของ record ที่ใกล้สุด สูงกว่า 0.45 ไหม" **กลไกนี้ผิดตั้งแต่ต้น**
ไม่ใช่โมเดลไม่ดี: `max cosine` เหนือ N เอกสารสูงขึ้นตาม N สำหรับ query อะไรก็ตาม
มี 1,102 เอกสาร ยังไงก็มีอันที่ดูคล้าย **ทดสอบ 5 โมเดล ไม่มีตัวไหนหา floor ที่แยกได้**

| กลไก | ขยะถูกกรอง | query จริงที่เสียไป |
|---|---|---|
| `cosine ≥ floor` (เดิม) | **0/5** | 0/12 |
| z-score — top hit โดดจากกลุ่มไหม | ยังทับกัน (margin −0.83 ถึง −0.93) | — |
| **`BM25 > 0` และ `cosine ≥ 0.50`** | **4/5** | **0/12** |

**ทำไม BM25 ชนะ:** ขยะไม่มีคำตรงกับ corpus เลย → ได้ **0.000 สนิท 4 จาก 5 ตัว**
ขณะที่ cosine หาอะไรคล้ายได้เสมอ ส่วน dense ยังต้องมีอยู่ เพื่อจับ query จริงที่ใช้คำต่างจาก corpus

**ตัวที่ยังหลุด:** `ๆๆๆ ฯฯฯ ฤฤฤ ฅฅฅ` — ๆ กับ ฯ เป็นอักขระไทยจริงที่มีใน corpus จึงมีคำตรงกันจริง
ไม่ใช่ bug ของกลไก แต่เป็นขอบเขตของมัน

## 6. ขนาด corpus ไม่ใช่ตัวแปรที่คิด

เคยเขียนไว้ว่า "corpus ยิ่งเล็ก ขยะยิ่งได้คะแนนสูง" **ผิด** วัดโดยสุ่มย่อยจาก corpus เดียวกัน:

| record | 25 | 50 | 100 | 200 | 400 | 936 |
|---|---|---|---|---|---|---|
| ขยะสูงสุด | 0.870 | 0.911 | 0.913 | 0.911 | 0.892 | 0.918 |

แบนและไม่เป็นเส้นตรง แต่ corpus **ต่างเนื้อหา** ที่ขนาดใกล้กันขยับเยอะ (0.581 / 0.767 / 0.918)
→ **เนื้อหากำหนด ไม่ใช่ขนาด** floor จึงเป็นคุณสมบัติของ corpus คู่กับโมเดล ต้องวัดที่หน้างาน

## 7. `0 blocked` บนข้อมูลจริง — cue ไม่ตรงภาษาทีม

digest บน `real_all.json` ได้ **37 active · 19 resolved · 0 blocked** ทั้งที่ "อะไรติด" คือฟีเจอร์หลัก

| cue ที่ระบบใช้ | เจอใน 936 ข้อความจริง |
|---|---|
| `ยังรอ` `ต้องรอ` `รออยู่` `ติดที่` `ยังไม่มา` `ยังทำไม่ได้` `blocked` `depends on` | **0 ทั้งหมด** |
| `waiting for` | 2 |
| คำที่ทีมใช้จริงแต่ไม่อยู่ในลิสต์: `pending` | 15 |
| `ค้าง` | 4 |

**กับดักสองอันที่ห้ามเติมมั่ว:**

1. **`รอ` เดี่ยวเจอ 92 ครั้ง แต่เกือบทั้งหมดผิด** — ภาษาไทยไม่มีเว้นวรรค `รอ` อยู่ใน
   "ร**อบ**" "ก**รอก**" "ห**รอ**" เช่นเดียวกับ `ติด` ที่อยู่ใน "ติดต่อ" "ติดตั้ง" "ติดตาม"
   **ทางแก้ที่ถูกคือตัดคำด้วย pythainlp แล้วแมตช์ระดับ token** — `รอบนี้` → `[รอบ, นี้]` ไม่มี token `รอ`
   แต่ `ยังรอ api อยู่` → `[ยัง, รอ, api, อยู่]` มี
2. **`blocker` 14 จาก 22 ครั้งมาจาก template standup** ที่ขึ้นหัวว่า "Any blockers?"
   เติมเป็น cue จะ fire ทุกโพสต์ standup

**สิ่งที่ระบบทำถูก:** มันรายงาน 0 ตรง ๆ **ไม่ได้แต่งงานติดขึ้นมา** ให้ดูดี

> สถานะข้อนี้: กำลังวิเคราะห์ว่าควรใช้คำอะไรจากข้อมูลจริง (5 มุมมอง + ผู้ค้านวัด precision)
> ผลจะมาเติมในหัวข้อนี้

## 7.5 ข้อมูลเพิ่มขึ้น 20% แล้ว — เทรนใหม่คุ้มไหม (ไม่)

หลังรวม ticket จาก YouTrack เข้า corpus จำนวน record ขึ้นจาก 974 เป็น **1,168 (+20%)**
คำถามที่ตามมาคือควรกลับไปเทรนใหม่ไหม เพราะเหตุผลเดิมที่ fine-tune แพ้คือ "corpus เล็กเกินไป"

**คำตอบคือไม่ และเหตุผลหนักกว่าเรื่องขนาด corpus** — ที่ขาดคือ *สัญญาณสอน* ไม่ใช่จำนวนข้อความ

สิ่งที่ ticket ให้เพิ่มเข้ามาซึ่ง thread ให้ไม่ได้คือ **คู่ที่มีป้ายกำกับแน่นอน**: ข้อความ Slack
ที่พิมพ์เลข ticket กับตัว ticket นั้น เป็นคู่บวกที่ไม่ต้องเดา วัดแล้วได้:

| | |
|---|---|
| คู่ (ข้อความ ↔ ticket) จากการอ้างอิงจริง | **23 คู่** |
| ticket ที่ถูกเอ่ยถึงใน Slack อย่างน้อย 1 ครั้ง | **19 / 194 ใบ (10%)** |
| ticket ที่ถูกเอ่ยถึง ≥2 ครั้ง | 4 ใบ |
| `MultipleNegativesRankingLoss` ต้องใช้จริงราว | 10,000+ คู่ |

23 คู่คือ **0.2%** ของที่ต้องใช้ และตัวเลข 19/194 บอกว่าทีมนี้แทบไม่พิมพ์เลข ticket ในแชท
เลย จึงไม่มีอะไรให้โมเดลเรียนว่า "ข้อความแบบนี้คือ ticket ใบนี้" การเทรนด้วยข้อมูลเท่านี้จะได้
ผลเหมือนสองรอบก่อน คือ cosine ของ query ขยะสูงขึ้นเพราะ space ยุบ ไม่ใช่ความแม่นที่ดีขึ้น

**เกณฑ์ที่จะทำให้กลับมาคิดใหม่:** คู่ที่มีป้ายกำกับถึงหลักพัน ซึ่งจะเกิดได้ถ้าทีมเริ่มพิมพ์เลข
ticket ในข้อความ (หรือดึง comment ใน YouTrack ซึ่งผูกกับ ticket อยู่แล้วโดยไม่ต้องให้ใครพิมพ์)
— **การดึง comment คือทางที่ถูกที่สุดที่จะได้สัญญาณจริง และยังไม่ได้ทำ**

## 7.6 resolution ของการจับกลุ่ม 1.0 → 4.0 — วัดสองทิศทาง

`/blockers` รายงานต่ำกว่าจริงมานาน และบันทึกเก่าในรีโปนี้เขียนว่า `resolution 4.0` ดันเพดาน
จาก 2 เป็น 4 **บันทึกนั้นผิด** วัดใหม่แล้ว blocked เท่ากับ **2 ทุกค่าตั้งแต่ 1.0 ถึง 6.0**
(บันทึกเก่าวัดไว้ก่อนแก้กฎ declaration) การจับกลุ่มไม่ใช่คอขวดของ blocker recall

แต่การวัดพาไปเจอปัญหาอื่นที่จริงกว่า — ที่ 1.0 งานชิ้นใหญ่สุดบนจอมี **132 ข้อความ**
ก้อนหนึ่งปน **ticket ต่างกัน 19 ใบ** ในการ 40 ข้อความ และก้อน median กิน 41 วันจาก
หน้าต่าง export 74 วัน นั่นคือแชนเนล ไม่ใช่งานหนึ่งชิ้น

เหตุผลที่ไม่ควรเพิ่ม resolution คือกลัวผ่างานจริงออกเป็นเสี่ยง จึงวัดทั้งสองทาง:

| resolution | topic | ticket ต่างกันในก้อนที่แย่สุด | เฉลี่ย/ก้อน | ticket ที่ข้อความอ้างถึงกระจายข้ามก้อน | งานใหญ่สุดบนจอ | ครอบคลุม |
|---|---|---|---|---|---|---|
| **1.0** | 37 | **19** | 4.82 | **31%** | **132 ข้อความ** | 90% |
| 2.0 | 48 | 16 | 4.56 | 15% | — | 89% |
| **4.0** | 61 | **7** | 2.72 | **9%** | **50 ข้อความ** | **85%** |
| 6.0 | 70 | 7 | 2.58 | 8% | — | 86% |

**ผ่าเกินลดลงเมื่อ resolution สูงขึ้น** ซึ่งกลับทางกับที่คาด เพราะที่ค่าต่ำ ก้อนใหญ่ดูดข้อความ
ตามช่องและเวลาไม่ใช่ตามเรื่อง คนสองคนที่คุย ticket เดียวกันในสองที่จึงไปอยู่สองก้อน **ไม่มี
tradeoff ให้เลือก — 1.0 แย่กว่าทั้งสองทาง** เลือก 4.0 เพราะเหนือกว่านั้นผลนิ่ง (7→7, 9%→8%)
แต่ standup ต้องอ่านมากขึ้น

**ต้นทุนที่ต้องพูด:** ครอบคลุม 90% → 85% เพราะก้อนเดี่ยวตกใต้ `min_messages` ข้อความเหล่านั้น
คือข้อความที่ไม่มีใครตอบเรื่องที่ไม่มีใครพูดถึงอีก — ยังอยู่ใน corpus และยังค้นเจอ แค่ไม่ถูกเรียกว่างาน
**blocked ทั้งสองอันและหลักฐานเหมือนเดิมเป๊ะ** จึงไม่มีอะไรเรื่องสถานะขึ้นอยู่กับค่านี้

## 10. ค้างไว้: gate ยังหลุด query ภาษาจริงที่ไม่มีเรื่องนั้นใน corpus

พบตอนสาธิตให้ผู้ใช้ดู ไม่ใช่ตอนวัด — ซึ่งบอกอะไรอยู่

`lexical > 0` กรอง**ขยะ**ได้ (ตามที่วัดใน §5) แต่กรอง **query ภาษาจริงที่ไม่มีเรื่องนั้น**
ไม่ได้ ตัวอย่าง: `แผนการตลาดไตรมาสหน้าที่สิงคโปร์` ได้ bm25 = 9.66 จึงผ่านประตู
เพราะ pythainlp ตัด `ไตรมาสหน้าที่` ได้ token `หน้าที่` ซึ่งไปแมตช์ข้อความสั้นในคลัง
ที่มีคำว่า `หน้าที่` อยู่ (ข้อความยาวไม่ถึงสิบคำ) และ BM25 ให้แต้มสูงกับเอกสารสั้น
**คำสามัญคำเดียวก็ผ่าน**
ผลที่โชว์กลับมาไม่มีคำตรงกับ query เลย (`terms = []`)

**ตัวที่ลองแล้วยังไม่พอ** — coverage แบบ "คำนี้มีใน corpus ไหม" ได้ 1.00 เกือบทุก query
เพราะคำไทยเกือบทุกคำโผล่ที่ไหนที่หนึ่งใน 936 ข้อความ

**ตัวที่น่าจะใช่ ยังไม่ลง** — idf-weighted coverage **ภายในเอกสารเดียว** โดยให้คำที่
ไม่เคยเจอใน corpus มี idf **สูงสุด** ไม่ใช่ 0 (จุดนี้เป็นบั๊กใน metric รอบแรก: ให้ 0
ทำให้ query ที่คำส่วนใหญ่ไม่มีอยู่ ดูเหมือนครอบคลุมเต็ม)

| ชนิด | coverage |
|---|---|
| ขยะ 3 แบบ | 0.00 · 0.00 · 0.25 |
| เรื่องที่ไม่มีใน corpus 3 แบบ | 0.19 · 0.22 · 0.22 |
| เรื่องที่มีจริง 5 แบบ | 0.32 · 0.41 · 0.57 · 1.00 · 1.00 |

เกณฑ์ราว **0.28** จะกรองได้ 6/6 และไม่เสีย query จริงเลย 5/5 — **margin เป็นบวกครั้งแรก**
ในบรรดากลไกที่ลองทั้งหมด (cosine floor, z-score, cross-encoder, lexical>0)

**ทำไมยังไม่ลง** 11 probe ที่ผู้เขียนเลือกเอง margin แค่ 0.07 และไม่มีชุด held-out
การตั้งเกณฑ์บนตัวอย่างที่ตัวเองเลือกคือสิ่งที่เอกสารนี้วิจารณ์ไว้ใน §5 เอง
ต้องมี probe ที่คนอื่นเขียน หรือ query จริงจาก log ก่อนจะเชื่อ
