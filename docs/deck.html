04จุดต่าง

“ทำไมไม่ต่อ Claude เข้า Slack แล้วถามมันเลย”

คำถามนี้ถูก และต้องตอบก่อนอย่างอื่น — Slack, Notion, Jira มี connector พร้อมใช้วันนี้ ถามว่า “อะไรติดอยู่” แล้วมันตอบได้จริง

เราจึงไม่ขายว่า “อ่าน Slack แล้วสรุปได้” — ข้อนั้นแพ้ และแพ้เพราะมันจริง สิ่งที่ผู้ช่วยแบบถาม-ตอบทำไม่ได้ ไม่ใช่ทำได้แย่กว่า มีสามข้อ

01 · ไม่มีใครถาม

คุณค่าเกิด 09:25 ก่อน standup และ 08:45 ใน DM อาการของปัญหาคือ “ลืมนึกถึง” — เครื่องมือที่ต้องเรียกใช้ แก้ปัญหาที่อาการคือการลืมเรียกใช้ไม่ได้

02 · ถามซ้ำได้คำตอบเดิม

ถาม LLM สองครั้งอาจได้สถานะไม่เท่ากัน standup ต้องการคำตอบที่ทำซ้ำได้ สถานะที่นี่คำนวณด้วยกฎ ไม่ผ่านโมเดล

03 · เฝ้าโดยไม่มีใครสั่ง

ไม่มีใครเปิดมาถามว่า “สัปดาห์นี้ ticket ไหนในหลายสิบใบ ไม่ตรงกับที่คุยใน Slack” การเฝ้าต้องยืนอยู่ตลอด

08ความปลอดภัย

ข้อมูลไม่ออกนอกเครื่อง — และนี่คือประตู ไม่ใช่ความชอบ

อีกสองจุดต่างที่ connector ผ่านไม่ได้ ค่า default ของระบบนี้ไม่ส่งข้อความออกนอกเครื่องเลย โมเดลทุกตัวรันในเครื่อง — สำหรับองค์กรที่ไม่อนุญาตให้ Slack ไหลออก API ต่างประเทศ นี่เป็นเงื่อนไขผ่าน/ไม่ผ่าน · และภาษาไทยที่วัดผลได้ ไทยไม่มีเว้นวรรค เราจึงใช้ Thai BM25 + character n-gram + multilingual embeddings และมีเลข recall/nDCG กำกับ ไม่ใช่ keyword search ที่เสื่อมเงียบๆ

รีโปเป็น public จึงต้องแยกให้ชัดว่าอะไรเผยแพร่ได้ อะไรไม่ได้ — และตรวจจริง ไม่ใช่ตั้งใจไว้

เกณฑ์ตัดความเกี่ยวข้องกรองผิดสัญญาณมาตลอด — การวัดคือสิ่งที่จับได้

แก้ที่กลไก ไม่ใช่ที่ตัวเลขเกณฑ์

cosine สูงสุดไม่ได้บอกว่า “มีของให้ตอบ” — มันบอกว่า corpus ใหญ่

gate เดิมถามข้อเดียว: cosine ของ record ที่ใกล้สุดถึงเกณฑ์ไหม แต่ max cosine เหนือ N เอกสารสูงขึ้นตาม N สำหรับ query อะไรก็ตาม — มี ~1,000 record ยังไงก็มีอันที่ดูคล้าย สไลด์นี้เวอร์ชันก่อนเขียนว่า MiniLM แยกขยะออกได้และตัวที่ fine-tune เองเป็นตัวที่พัง ข้อนั้นผิด: วัดบน corpus จริงแล้ว ไม่มีโมเดลไหนในห้าตัวที่มี floor ซึ่งแยกได้ MiniLM รวมอยู่ในนั้นด้วย

กลไกที่ลองขยะที่กรองได้query จริงที่เสียไป
cosine ≥ floor เดี่ยว (ของเดิม)0/5 — ทั้งห้าโมเดล0/12
cross-encoder reranker เป็น gateปฏิเสธ — คำถามไทยจริงได้ 0.008 ขณะที่ขยะได้ 0.114—
BM25 > 0 และ cosine ≥ floor (ใช้ตัวนี้)4/50/12

ทำไมสัญญาณคำถึงชนะ: ขยะไม่มีคำตรงกับ corpus เลย BM25 จึงได้ 0.000 สนิท ขณะที่ cosine หาอะไรคล้ายได้เสมอ — บน corpus ตัวอย่าง 27 record ที่ commit ไว้ query ขยะได้ bm25 0.00 · cos 0.486 คือผ่านเกณฑ์ cosine 0.45 แต่ตกที่สัญญาณคำ ส่วน dense ยังต้องมีอยู่ เพื่อจับคำถามจริงที่ใช้คำต่างจาก corpus · /api/search จึงคืน relevance: {lexical, dense} เป็นค่าดิบทั้งคู่ และ pipeline ที่เก่าเกินจะส่งฟิลด์นี้ throw ทิ้ง ไม่ปล่อยผ่านเงียบ ๆ

⚠ ขอบเขตที่ยังอยู่ ตัวที่ยังหลุดคืออักขระไทยซ้ำ ๆ (ๆ ฯ) ซึ่งมีอยู่ในข้อความปกติจริง จึงมีคำตรงกันจริง — check-api เก็บ probe ตัวนี้ไว้ในลิสต์ตั้งใจ และรายงาน 3/4 แทนที่จะซ่อนให้ดูสวย · บน corpus จริงที่รันอยู่: กรองขยะ 3/4 เสีย query จริง 0/6 · บน corpus ตัวอย่าง 27 record มันกรองขยะได้ 4/4 แต่ตัด probe จริงทิ้ง 1 อัน ซึ่งเป็น label ที่ไม่มีคำร่วมกับ corpus เลย ((no shared anchor)) ไม่ใช่คำถามที่คนพิมพ์ — corpus เล็กก็เห็นทั้งสองด้านของกลไกชัดกว่า

ปิดไปแล้ว

บอทกับ pipeline นับ “งานหนึ่งชิ้น” เหมือนกันแล้ว

เดิมสองฝั่งอ่าน Slack เองและจับกลุ่มด้วยกฎต่างกัน ช่องเดียวกันจึงได้ work item ไม่เท่ากัน ตอนนี้ตั้ง TAM_API_URL แล้วบอทเลิกตัดสินเอง — work item, สถานะ, หลักฐาน, timeline และ recall มาจาก pipeline ทั้งหมด

✓ ทดสอบแล้ว npm run check-api บนข้อมูลจริง: 20 work item · หลักฐาน, citation และ timeline ทุกอันชี้ข้อความที่มีจริงใน item นั้น · permalink สร้างได้ 694/694 ข้อความที่มาจาก Slack (ที่เหลือมาจากไฟล์ประชุม จึงไม่มี permalink ตามคาด) · standup draft 17 อันคำนวณจาก item ที่ได้มา ส่วน decision 0 เพราะยังไม่มีคนกดบันทึก — ไม่เติมให้ดูเต็ม · exit code ตอบแค่ว่า “รอยต่อนี้ถูกไหม” (ได้ 0) การ calibrate เกณฑ์รายงานให้เห็นแต่ไม่ทำให้ fail เว้นใส่ --strict-gate (แล้วได้ 1) เพราะ floor เป็นคุณสมบัติของ corpus คู่กับโมเดล ไม่ใช่ของรอยต่อ

ปิดไปแล้ว

ต่อ ticket system จริงแล้ว — และแหล่งที่สองเจอสิ่งที่ Slack เงียบสนิท

ticket อยู่ใน corpus เดียวกันกับ Slack แล้ว ไม่ใช่แค่เอามาเทียบ — ค้นครั้งเดียวเจอทั้งสองแหล่ง สิ่งที่ embed คือชื่อ ticket บวก 2 บรรทัดแรกของ description ที่มีเนื้อหาจริง (ไม่ใช่ทั้งก้อน: median ของ Slack อยู่ที่ 46 ตัวอักษร ของ ticket 582 และมีใบหนึ่ง 14,556 ซึ่งเป็นตาราง test case ล้วน) และ ticket ห้ามตั้งตัวเป็นงานเอง — 82 จาก 194 ใบไปเกาะกับบทสนทนาจริง อีก 112 ใบยุบเป็น 3 ก้อนที่แทบไม่มีคนคุย จึงถูกกันออกจาก digest แต่ยังค้นเจอครบ อ่าน ticket จริง 195 ใบ (เปิดค้าง 61) มาเทียบกับที่คุยใน Slack ผลที่ได้ไม่ใช่ลิสต์ ticket เก่า แต่เป็นรูปแบบ: 24 ใบเงียบเกิน 21 วัน · 22 ใบอยู่สถานะ Ready for test และวันที่ถูกแตะครั้งสุดท้ายกระจุกอยู่แค่ 2 วัน — 11 ใบวันเดียวกัน (เงียบ 56 วัน) และ 10 ใบอีกวัน (เงียบ 22 วัน) แปลว่างานถูกดันเข้า QA เป็นก้อน ๆ แล้วไม่มีใครหยิบต่อ ก้อนเก่าค้างมา 8 สัปดาห์ โดยไม่มีข้อความใน Slack พูดถึงเลยแม้แต่คำเดียว

เกณฑ์ 21 วันมาจากจังหวะของทีมเอง ไม่ใช่ความรู้สึก — วันที่ ticket เปิดอยู่ไม่ถูกแตะมี p25 = 5 · median = 8 · p75 = 22 และ 21 ตกในช่องว่างธรรมชาติ (ไม่มี ticket ใบไหนอยู่ระหว่าง 14–21 วัน) เกณฑ์จึงไม่ผ่ากลางกลุ่มหนาแน่นที่เลื่อนวันเดียวคำตอบเปลี่ยน

⚠ รายงานให้ตรง เงื่อนไข “ไม่มีใครพูดถึงใน Slack” ไม่ได้ใช้เป็นตัวกรอง เพราะวัดแล้วมันไม่เปลี่ยนอะไร (24 จาก 24 ที่เกณฑ์นี้) — ใส่เป็นตัวกรองจะทำให้ดูเหมือนต้องใช้สองแหล่งทั้งที่ไม่ใช่ · และ “ไม่มีใครพูดถึง” จำกัดอยู่ในหน้าต่าง 74 วันที่ export มา ไม่ใช่ทั้งประวัติ · ถ้าอ่าน ticket ไม่ได้ /api/tracker ส่ง error มาคู่กับลิสต์ว่าง และหน้าจอเขียนว่า “เรายังไม่รู้” ไม่ใช่ “ไม่มีงานค้าง”

✓ ความครอบคลุม ตัวนี้ครอบคลุม 100% ของ ticket ที่เปิดค้าง เพราะไม่ต้องรอให้ Slack เอ่ยถึง ต่างจากการเทียบสถานะที่ทำได้แค่ 11 จาก 28 work item ที่ผูกกับ ticket ได้ — และ drift ต้องมีคนพิมพ์เลข ticket จริง ซึ่งเกิดขึ้นกับ 19 จาก 194 ใบ (10%) เท่านั้น

ข้อจำกัดที่เหลือ

/blockers ยังรายงานต่ำกว่าความจริง — อ่านด้วยมือพบ blocker จริง 22 ข้อความ แต่รายงานได้ 2 · ไล่ตัดผู้ต้องสงสัยด้วยการวัดแล้วครบ — ไม่ใช่การจับกลุ่ม (blocked = 2 เท่ากันทุกค่า resolution 1.0–6.0 · บันทึกเก่าที่ว่า 4.0 ดันเป็น 4 นั้นผิด) และไม่ใช่ลิสต์คำ (ลอง `pending` ที่โผล่ 15 ครั้ง ได้ blocked 3 แต่หลักฐานคือโพสต์ “Sprint 3 is officially end RECAP” จึงถอนออก) · คอขวดคือระดับของสัญญาณ — ทีมเขียน blocker เป็นบรรทัดหนึ่งในโพสต์ daily ที่ยาวกว่าข้อความปกติ 12 เท่า (529 vs 46 ตัวอักษร · 14 จาก 15 เป็นโพสต์หลายบรรทัด) และมักระบุตัวคนที่รออยู่ เช่น “insurance pending from mild” แต่ทั้ง cue matcher และตัวตัดสินสถานะทำงานที่ระดับข้อความ ก้าวถัดไปคืออ่านระดับบรรทัด ซึ่ง ingest/standup.py ทำได้แล้วกับฟอร์ม · reply ในเธรดยังไม่ถูกนับ corpus มี 1,144 record แต่ตัวโหลดตัด slack_thread ออก 170 อันตาม default (include_threads=False) เหลือ 974 — ในนั้น 110 อันเป็นเนื้อหาใหม่จริง และมีข้อความขอความช่วยเหลือตรง ๆ อยู่ด้วย เปิดใช้เป็นการแก้ flag เดียว แต่ยังไม่ได้วัดว่ากระทบการจับกลุ่มยังไง จึงไม่เปลี่ยนก่อนวัด · ภาษาไทยไม่เว้นวรรค คำว่า รอ ไปเจอใน “รอบ” “กรอก” จึงต้องตัดคำแล้วแมตช์ระดับ token

ขยายไม่ได้ถ้าโตมาก

ค้นหาแบบ brute-force ไหวระดับหลายพันข้อความ ไม่ไหวระดับล้าน — ต้องมี vector database · bge-m3 ใหญ่และช้ากว่าตัวเดิม รับได้เพราะ embedding ถูก cache ไว้แล้ว

  • ก้าวถัดไปที่ 1 หา cue ของ “ติด” จากข้อมูลจริง แล้ววัด precision ก่อนเชื่อ — ไม่เติมคำแล้วเคลม (คำอย่าง blocker 14 จาก 22 ครั้งมาจาก template standup ที่ขึ้นหัวว่า “Any blockers?” เติมเข้าไปจะ fire ทุกโพสต์)
  • ก้าวถัดไปที่ 2 ต่อ ticket system แบบอ่านจริง ให้ drift ซึ่งเป็นจุดต่างข้อ 03 ทำงานกับข้อมูลจริง ไม่ใช่ fixture
  • ก้าวถัดไปที่ 3 ถ้าจะกลับมาเทรนโมเดลอีก ต้องเปลี่ยนฐานเป็น bge-m3 และหาข้อมูลมากกว่านี้หลายเท่า — เทรนบน MiniLM ต่อด้วย corpus ระดับนี้ วัดแล้วว่าไม่คุ้ม
