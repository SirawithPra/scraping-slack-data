02ปัญหา

สถานะจริงของงานอยู่ใน 4 ที่ และครบอยู่ที่เดียว — ในหัวคน

อาการที่ทีมเจอดูเหมือนหลายเรื่อง แต่เป็นเรื่องเดียวกันในเสื้อผ้าคนละชุด

เช้าวันจันทร์

เข้า standup แล้วต้องนึกเองว่าใครติดอะไรไว้เมื่อวันศุกร์

งานที่หายไป

เรื่องที่คุยกันในเธรดแล้วไม่มีใครเปิด ticket ก็หายไปเลย

requirement เปลี่ยน

ตกลงกันใหม่ใน Slack แต่ ticket ยังเป็นของเดือนพฤษภาคม

ถามซ้ำ

"เรื่องนี้สรุปว่าอะไร" ถูกถามใหม่ทุกสองสัปดาห์ เพราะไม่มีที่ให้ย้อนดู

เครื่องมือที่มีอยู่แก้ไม่ตรงจุด — bot รวบรวม standup ได้แต่ต้องให้คนพิมพ์เอง, dashboard สวยแต่ข้อมูลต้องกรอก, ticket system รู้แต่เรื่องที่มีคนเปิด ticket

อ้างอิง docs/DESIGN_BRIEF.mdขอบเขต ทีมซอฟต์แวร์ที่คุยงานใน Slack เป็นหลัก
03ทางแก้

รวมเป็น "งานหนึ่งชิ้น" แล้วส่งให้ตอนที่คุณกำลังใช้ความจำ

ไม่ใช่ dashboard เพิ่มอีกอัน — เป็นระบบที่อ่านสิ่งที่ทีมพิมพ์กันอยู่แล้ว แล้วเก็บเป็นบันทึกเดียวต่อหนึ่งงาน

ข้อความ Slack + เธรด  +  บันทึกการประชุม (VTT / SRT)
→ ทำความสะอาด กรอง noise ให้เป็น record รูปแบบเดียวกัน
→ จับกลุ่มเป็น work item · คำนวณสถานะ · ผูกหลักฐานทุกข้อ
→ อ่านได้ 3 ทาง: CLI · Dashboard · ในหน้าต่าง Slack เอง

จุดที่ต่างจริง คือการประชุมไม่ได้เป็น pipeline ที่สอง — บันทึกการประชุมถูกแปลงเป็น record ชนิดเดียวกับ Slack ทำให้งานหนึ่งชิ้นข้ามสองแหล่งได้โดยไม่ต้องเขียนโค้ดใหม่

ตัวอย่างที่ commit ไว้ standup.vtt → 9 record ชนิดเดียวกับ Slack ในไฟล์เดียวกัน (27 record รวม)ไม่มี pipeline ที่สอง tam.ingest.meetings --merge-into เขียนลง corpus เดิม
04จุดต่าง

“ทำไมไม่ต่อ Claude เข้า Slack แล้วถามมันเลย”

คำถามนี้ถูก และต้องตอบก่อนอย่างอื่น — Slack, Notion, Jira มี connector พร้อมใช้วันนี้ ถามว่า “อะไรติดอยู่” แล้วมันตอบได้จริง

เราจึงไม่ขายว่า “อ่าน Slack แล้วสรุปได้” — ข้อนั้นแพ้ และแพ้เพราะมันจริง สิ่งที่ผู้ช่วยแบบถาม-ตอบทำไม่ได้ ไม่ใช่ทำได้แย่กว่า มีสามข้อ

01 · ไม่มีใครถาม

คุณค่าเกิด 09:25 ก่อน standup และ 08:45 ใน DM อาการของปัญหาคือ “ลืมนึกถึง” — เครื่องมือที่ต้องเรียกใช้ แก้ปัญหาที่อาการคือการลืมเรียกใช้ไม่ได้

02 · ถามซ้ำได้คำตอบเดิม

ถาม LLM สองครั้งอาจได้สถานะไม่เท่ากัน standup ต้องการคำตอบที่ทำซ้ำได้ สถานะที่นี่คำนวณด้วยกฎ ไม่ผ่านโมเดล

03 · เฝ้าโดยไม่มีใครสั่ง

ไม่มีใครเปิดมาถามว่า “สัปดาห์นี้ ticket ไหนในหลายสิบใบ ไม่ตรงกับที่คุยใน Slack” การเฝ้าต้องยืนอยู่ตลอด

5 API + health

ข้อมูลชุดเดียวกันออกเป็น JSON — /api/digest · /api/blockers · /api/item/{key} · /api/search · /api/health และ POST /api/reindex ที่ต้องมี token

✓ ทดสอบแล้ว ยิงทั้ง 10 endpoint ที่อ่านข้อมูล (5 หน้า + 5 API) คืน 200 พร้อมเนื้อหาจริงทุกตัว · อีก 2 route ที่เขียนข้อมูล (POST /upload, POST /api/reindex) ต้องแนบ token ที่ server พิมพ์ตอน start

⚠ อ่านตัวเลขนี้ให้ตรง blocked เป็น 0 ไม่ได้แปลว่าไม่มีใครติด — คำ cue ที่ระบบใช้ไม่ตรงกับคำที่ทีมพิมพ์จริง ระบบรายงาน 0 ตรง ๆ แทนที่จะเดาให้ดูดี (ดูสไลด์ 10)

ไม่มี build step HTML สร้างจาก Python ตรง ๆ ไม่มี node_modulesไม่มี Slack ก็รันได้ data/sample/ commit ไว้แล้วlog สะอาด warning เท็จจาก BLAS ปิดเฉพาะจุด — ตรวจกับ float64 แล้วว่าตรงกันถึง 5e-08

08ความปลอดภัย

ข้อมูลไม่ออกนอกเครื่อง — และนี่คือประตู ไม่ใช่ความชอบ

อีกสองจุดต่างที่ connector ผ่านไม่ได้ ค่า default ของระบบนี้ไม่ส่งข้อความออกนอกเครื่องเลย โมเดลทุกตัวรันในเครื่อง — สำหรับองค์กรที่ไม่อนุญาตให้ Slack ไหลออก API ต่างประเทศ นี่เป็นเงื่อนไขผ่าน/ไม่ผ่าน · และภาษาไทยที่วัดผลได้ ไทยไม่มีเว้นวรรค เราจึงใช้ Thai BM25 + character n-gram + multilingual embeddings และมีเลข recall/nDCG กำกับ ไม่ใช่ keyword search ที่เสื่อมเงียบๆ

รีโปเป็น public จึงต้องแยกให้ชัดว่าอะไรเผยแพร่ได้ อะไรไม่ได้ — และตรวจจริง ไม่ใช่ตั้งใจไว้

แก้ที่กลไก ไม่ใช่ที่ตัวเลขเกณฑ์

cosine สูงสุดไม่ได้บอกว่า “มีของให้ตอบ” — มันบอกว่า corpus ใหญ่

gate เดิมถามข้อเดียว: cosine ของ record ที่ใกล้สุดถึงเกณฑ์ไหม แต่ max cosine เหนือ N เอกสารสูงขึ้นตาม N สำหรับ query อะไรก็ตาม — มี ~1,000 record ยังไงก็มีอันที่ดูคล้าย สไลด์นี้เวอร์ชันก่อนเขียนว่า MiniLM แยกขยะออกได้และตัวที่ fine-tune เองเป็นตัวที่พัง ข้อนั้นผิด: วัดบน corpus จริงแล้ว ไม่มีโมเดลไหนในห้าตัวที่มี floor ซึ่งแยกได้ MiniLM รวมอยู่ในนั้นด้วย

กลไกที่ลองขยะที่กรองได้query จริงที่เสียไป

cross-encoder reranker เป็น gateปฏิเสธ — คำถามไทยจริงได้ 0.008 ขณะที่ขยะได้ 0.114—

ทำไมสัญญาณคำถึงชนะ: ขยะไม่มีคำตรงกับ corpus เลย BM25 จึงได้ 0.000 สนิท ขณะที่ cosine หาอะไรคล้ายได้เสมอ — บน corpus ตัวอย่าง 27 record ที่ commit ไว้ query ขยะได้ bm25 0.00 · cos 0.486 คือผ่านเกณฑ์ cosine 0.45 แต่ตกที่สัญญาณคำ ส่วน dense ยังต้องมีอยู่ เพื่อจับคำถามจริงที่ใช้คำต่างจาก corpus · /api/search จึงคืน relevance: {lexical, dense} เป็นค่าดิบทั้งคู่ และ pipeline ที่เก่าเกินจะส่งฟิลด์นี้ throw ทิ้ง ไม่ปล่อยผ่านเงียบ ๆ

⚠ ขอบเขตที่ยังอยู่ ตัวที่ยังหลุดคืออักขระไทยซ้ำ ๆ (ๆ ฯ) ซึ่งมีอยู่ในข้อความปกติจริง จึงมีคำตรงกันจริง — check-api เก็บ probe ตัวนี้ไว้ในลิสต์ตั้งใจ และรายงาน 3/4 แทนที่จะซ่อนให้ดูสวย · บน corpus จริงที่รันอยู่: กรองขยะ 3/4 เสีย query จริง 0/6 · บน corpus ตัวอย่าง 27 record มันกรองขยะได้ 4/4 แต่ตัด probe จริงทิ้ง 1 อัน ซึ่งเป็น label ที่ไม่มีคำร่วมกับ corpus เลย ((no shared anchor)) ไม่ใช่คำถามที่คนพิมพ์ — corpus เล็กก็เห็นทั้งสองด้านของกลไกชัดกว่า

ข้อจำกัดที่เหลือ

คำ cue ไม่ตรงภาษาที่ทีมใช้ จึงได้ 0 blocked ทั้งที่ “อะไรติด” คือฟีเจอร์หลัก — และเติมคำมั่วไม่ได้ ภาษาไทยไม่เว้นวรรค คำว่า รอ ไปเจอใน “รอบ” “กรอก” ต้องตัดคำแล้วแมตช์ระดับ token · แปลง user id เป็นชื่อคนยังไม่มี (ต้องเพิ่ม scope users:read) · drift ยังไม่มีแหล่งจริง

ขยายไม่ได้ถ้าโตมาก

ค้นหาแบบ brute-force ไหวระดับหลายพันข้อความ ไม่ไหวระดับล้าน — ต้องมี vector database · bge-m3 ใหญ่และช้ากว่าตัวเดิม รับได้เพราะ embedding ถูก cache ไว้แล้ว

  • ก้าวถัดไปที่ 1 หา cue ของ “ติด” จากข้อมูลจริง แล้ววัด precision ก่อนเชื่อ — ไม่เติมคำแล้วเคลม (คำอย่าง blocker 14 จาก 22 ครั้งมาจาก template standup ที่ขึ้นหัวว่า “Any blockers?” เติมเข้าไปจะ fire ทุกโพสต์)
  • ก้าวถัดไปที่ 2 ต่อ ticket system แบบอ่านจริง ให้ drift ซึ่งเป็นจุดต่างข้อ 03 ทำงานกับข้อมูลจริง ไม่ใช่ fixture
  • ก้าวถัดไปที่ 3 ถ้าจะกลับมาเทรนโมเดลอีก ต้องเปลี่ยนฐานเป็น bge-m3 และหาข้อมูลมากกว่านี้หลายเท่า — เทรนบน MiniLM ต่อด้วย corpus ระดับนี้ วัดแล้วว่าไม่คุ้ม
