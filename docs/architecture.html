ตาม (Tam) · สถาปัตยกรรมและ flow

ข้อความหนึ่งข้อความ เดินทางไปเป็นการ์ดใน Slack ได้อย่างไร

ห้าภาพ ภาพละหนึ่งเรื่อง — เส้นทางข้อมูลทั้งเส้น, การให้คะแนน query หนึ่งครั้ง, ใครเป็นเจ้าของนิยาม “งานหนึ่งชิ้น”, การเขียนกลับเมื่อคนแก้, และด่านที่ทำให้ recall ตอบได้ว่า “ไม่เจอ” แล้วปิดท้ายด้วย โครงโฟลเดอร์ ทุกชื่อโมดูลในภาพคือไฟล์ที่มีอยู่จริงในรีโป

1 · เส้นทางทั้งเส้น

เรื่องสำคัญที่สุดของภาพนี้อยู่กลางภาพ: Slack กับบันทึกการประชุมถูกแปลงเป็น record รูปแบบเดียวกัน ตั้งแต่ต้น ทุกขั้นหลังจากนั้นจึงไม่ต้องรู้ว่าข้อความมาจากไหน งานหนึ่งชิ้นข้ามสองแหล่งได้โดยไม่มีโค้ดพิเศษ

2 · query หนึ่งครั้ง ได้คะแนนมาอย่างไร

cosine ตัวเดียวตอบไม่ครบ เพราะมันสมมาตร มองไม่เห็นสตริงตรงตัวอย่าง REV-1421 และไม่รู้ว่าสองข้อความอยู่เธรดเดียวกันห่างกันห้านาที แต่ละอย่างเป็นหลักฐานต่างชนิดกัน ภาพนี้คือลำดับที่มันถูกรวม

3 · ใครเป็นเจ้าของนิยาม “งานหนึ่งชิ้น”

เดิมสองฝั่งอ่าน Slack เองและจับกลุ่มด้วยกฎต่างกัน ช่องเดียวกันจึงได้ work item ไม่เท่ากัน และคำตอบที่ทีมเห็นขึ้นอยู่กับว่าเปิดที่ไหน ตั้ง TAM_API_URL แล้วเหลือเจ้าของเดียว

4 · คนแก้แล้วระบบจำ — วงเขียนกลับ

การจับกลุ่มอัตโนมัติผิดได้ และเมื่อคนแก้ ระบบต้องไม่เดาทับรอบหน้า linker.py มีชั้น override ที่ชนะทุกชั้นอยู่แล้ว และ load_overrides ของมันเขียนไว้ว่ารับ “the list-of-events shape a UI would append to” — วงนี้จึงปิดที่จุดที่ถูกออกแบบเผื่อไว้

5 · ด่านที่ทำให้ recall ตอบว่า “ไม่เจอ” ได้

คะแนนรวมคิดจากอันดับ ไม่ใช่ความคล้าย มันจึงบอกไม่ได้ว่า “ไม่เจออะไรเลย” — วัดบน corpus จริง อันดับ 1 ของ qqqzzzxxx wvwvwv jjjkkk zzzqqq ได้ 0.0328 ส่วนอันดับ 1 ของคำถามจริงได้ 0.0297 คือขยะได้คะแนนสูงกว่า และ why ของแต่ละแถวถูก normalise ในชุดผลลัพธ์ของตัวเอง อันดับ 1 จึงอ่านได้ 1.00 ทั้งสองแบบ ตัวเลขที่เทียบข้าม query ได้จึงมีแค่สองตัวที่ /api/search ส่งมาให้ต่างหาก — relevance.lexical (BM25 ดิบ) กับ relevance.dense (cosine ดิบ) — และด่านต้องใช้ทั้งคู่ ไม่ใช่ตัวใดตัวเดียว

6 · หลักการคิด — และการวัดที่ทำให้ได้หลักการนั้น

ห้าข้อนี้ไม่ได้ตั้งไว้ก่อนเริ่มเขียน ทุกข้อมาจากบั๊กที่วัดเจอแล้วต้องกลับไปแก้กลไก ไม่ใช่แก้ตัวเลข — คอลัมน์ขวาคือเรื่องที่ทำให้ได้ข้อนั้นมา

หลักการเจอมาจากอะไร
ทุกคำตอบต้องชี้ข้อความที่เป็นหลักฐาน
ถ้าอธิบายไม่ได้ว่ารู้มาจากไหน ก็ไม่ต้องพูด		 สถานะทุกอันเก็บ evidence_id ของข้อความที่ทำให้สรุปแบบนั้น พอเก็บแล้วบั๊กโผล่เอง — PROJ-157 ถูกมาร์คว่าปิดแล้วโดยอ้าง “added permission done krub” ซึ่งไม่มีคำว่า PROJ-157 อยู่เลย
กฎที่อธิบายได้ ชนะโมเดลที่เดาเก่ง
ใช้ embedding หา ใช้กฎตัดสิน		 สถานะมาจาก typed relation ที่ระบุ cue ได้ ไม่ได้มาจาก LLM เวลาผิดจึงชี้ได้ว่าผิดที่บรรทัดไหนแล้วแก้ได้ — และแก้ไปแล้วสามครั้งด้วยวิธีนี้
วัดสองทิศทาง ไม่ใช่ทิศที่นับง่าย
เลขที่ขึ้นง่ายมักขึ้นเพราะเหตุผลผิด		 จะเพิ่ม resolution ของการจับกลุ่ม ต้องวัดทั้ง ยุบเกิน และ ผ่าเกิน พร้อมกัน ปรากฏว่าลดทั้งคู่ — ไม่มี tradeoff ที่กลัวไว้ (ดูกราฟ 7a)
เทียบกับเรื่องเดียวกัน ไม่ใช่กับสิ่งที่อยู่ใกล้กัน
อยู่คลัสเตอร์เดียวกัน ไม่ใช่หลักฐาน		 บั๊กชนิดเดียวกันเกิดสามครั้ง: drift เทียบกับหางของคลัสเตอร์ · คำประกาศว่าติดถูกยกเลิก ด้วย cue ของคนอื่น · ticket ถูกเทียบเพราะ record มันนั่งอยู่ในก้อนเดียวกัน ทั้งสามครั้งแก้ด้วยการบังคับว่าต้องเป็นเรื่องเดียวกัน
“ไม่รู้” ต้องต่างจาก “ไม่มี”
ลิสต์ว่างเป็นคำตอบได้ ถ้ามันบอกว่าว่างเพราะอะไร		 recall ปฏิเสธ query ที่ไม่มีคำร่วมกับ corpus แทนที่จะเดาห้าอัน · /api/tracker ส่ง error มาคู่กับลิสต์ว่างเมื่ออ่าน ticket ไม่ได้ และหน้าจอเขียนว่า “เรายังไม่รู้” ไม่ใช่ “ไม่มีงานค้าง”

7 · กราฟจากตัวเลขที่วัดจริง

ทุกตัวเลขในหัวข้อนี้มาจากการรันบน corpus จริง ไม่ใช่ตัวอย่าง — ตัวเลขปัจจุบันรวมบันทึกประชุมที่ mock ไว้สองอันเพื่อทดสอบการรวมสามแหล่ง

8 · สองแหล่งกลายเป็น corpus เดียว — และกฎที่กันไม่ให้มันกลืนกัน

โครงโฟลเดอร์

สองฝั่งเป็นคู่กัน อยู่ระดับเดียวกัน และเข้าแบบเดียวกัน — cd pipeline กับ cd slack-bot แต่ละฝั่งมี .env.example, Slack app manifest และ data/ ของตัวเอง
