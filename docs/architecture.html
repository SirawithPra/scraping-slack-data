ตาม (Tam) · สถาปัตยกรรมและ flow

ข้อความหนึ่งข้อความ เดินทางไปเป็นการ์ดใน Slack ได้อย่างไร

ห้าภาพ ภาพละหนึ่งเรื่อง — เส้นทางข้อมูลทั้งเส้น, การให้คะแนน query หนึ่งครั้ง, ใครเป็นเจ้าของนิยาม “งานหนึ่งชิ้น”, การเขียนกลับเมื่อคนแก้, และเหตุผลที่ recall ต้องยิงสองครั้ง แล้วปิดท้ายด้วย โครงโฟลเดอร์ ทุกชื่อโมดูลในภาพคือไฟล์ที่มีอยู่จริงในรีโป

1 · เส้นทางทั้งเส้น

เรื่องสำคัญที่สุดของภาพนี้อยู่กลางภาพ: Slack กับบันทึกการประชุมถูกแปลงเป็น record รูปแบบเดียวกัน ตั้งแต่ต้น ทุกขั้นหลังจากนั้นจึงไม่ต้องรู้ว่าข้อความมาจากไหน งานหนึ่งชิ้นข้ามสองแหล่งได้โดยไม่มีโค้ดพิเศษ

2 · query หนึ่งครั้ง ได้คะแนนมาอย่างไร

cosine ตัวเดียวตอบไม่ครบ เพราะมันสมมาตร มองไม่เห็นสตริงตรงตัวอย่าง REV-1421 และไม่รู้ว่าสองข้อความอยู่เธรดเดียวกันห่างกันห้านาที แต่ละอย่างเป็นหลักฐานต่างชนิดกัน ภาพนี้คือลำดับที่มันถูกรวม

3 · ใครเป็นเจ้าของนิยาม “งานหนึ่งชิ้น”

เดิมสองฝั่งอ่าน Slack เองและจับกลุ่มด้วยกฎต่างกัน ช่องเดียวกันจึงได้ work item ไม่เท่ากัน และคำตอบที่ทีมเห็นขึ้นอยู่กับว่าเปิดที่ไหน ตั้ง TAM_API_URL แล้วเหลือเจ้าของเดียว

4 · คนแก้แล้วระบบจำ — วงเขียนกลับ

การจับกลุ่มอัตโนมัติผิดได้ และเมื่อคนแก้ ระบบต้องไม่เดาทับรอบหน้า linker.py มีชั้น override ที่ชนะทุกชั้นอยู่แล้ว และ load_overrides ของมันเขียนไว้ว่ารับ “the list-of-events shape a UI would append to” — วงนี้จึงปิดที่จุดที่ถูกออกแบบเผื่อไว้

5 · ทำไม recall ต้องยิงสองครั้ง

คะแนนรวมหลัง RRF คิดจากอันดับ ไม่ใช่ความคล้าย มันจึงบอกไม่ได้ว่า “ไม่เจออะไรเลย” เลยแม้แต่นิดเดียว — อันดับ 1 ได้ 1/61 + 1/61 = 0.0328 เท่ากันทุก query ไม่ว่าจะเป็นคำถามจริง หรือ qqqzzzxxx wvwvwv jjjkkk zzzqqq เพราะอันดับ 1 ในสอง stage ก็คืออันดับ 1 ในสอง stage ถ้าไม่มีด่าน recall จะตอบทุก query ด้วยผลลัพธ์ห้าแถวที่ดูน่าเชื่อ ซึ่งเป็นพฤติกรรมกล่องดำที่โปรดักต์นี้มีอยู่เพื่อไม่ให้เกิด

โครงโฟลเดอร์

สองฝั่งเป็นคู่กัน อยู่ระดับเดียวกัน และเข้าแบบเดียวกัน — cd pipeline กับ cd slack-bot แต่ละฝั่งมี .env.example, Slack app manifest และ data/ ของตัวเอง
