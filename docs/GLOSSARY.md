# ศัพท์ที่ต้องเข้าใจก่อนขึ้นนำเสนอ

ทุกคำในนี้ปรากฏจริงในโค้ด เอกสาร หรือหน้าจอของโปรเจกต์นี้ ไม่ได้ใส่มาเพื่อความครบ
คอลัมน์ที่สามคือ **เลข/ที่อยู่จริงในโปรเจกต์** — อ่านคอลัมน์นี้เวลาถูกถามว่า "แล้วของเราเท่าไหร่"

เรียงจากคำที่คนถามบ่อยที่สุดลงไปหาคำที่ลึกที่สุด ถ้ามีเวลาอ่านแค่สองหัวข้อ ให้อ่าน §1 และ §11

---

## 1. ข้อมูลและคลังข้อมูล

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **corpus** | คลังข้อความทั้งก้อนที่ระบบใช้ทำงาน — ทั้งค้นหา ทั้งจัดกลุ่ม ทั้งวัดผล พูดว่า "corpus 936 record" = ระบบเห็นข้อความ 936 ชิ้นนี้เท่านั้น ไม่รู้อะไรนอกนี้ | มี 4 ก้อน: sample ที่ commit (22–29 record), synthetic chat (927), private export เล็ก (33), คลังจริงที่รันอยู่ (**1,301 record ที่ตัวโหลดใช้ จากไฟล์ 1,492** — Slack 1,079 · reply ในเธรด 191 ที่ตัดออกตาม default · ทิกเก็ต YouTrack 196 · ประชุม 24 · โน้ต 2 · วัด 19 ส.ค. 2569 23:24 และโตทุกเช้าที่งานดึงข้อมูลรัน) |
| **record** | หนึ่งแถวที่ค้นหาได้ อาจเป็นข้อความเดี่ยว, thread ที่ต่อกันเป็นก้อน, หรือ 1 ประโยคในที่ประชุม → **record ≠ message** จำนวนจึงไม่เท่ากัน | ไฟล์คลังจริงมี 1,492 record แต่ตัวโหลด default ตัด `slack_thread` 191 อันออก เหลือ **1,301 record ที่ค้นหาได้** (ที่หายตอน ingest คือข้อความว่าง/bot/สั้นเกิน) |
| **message** | ข้อความดิบ 1 ข้อความใน Slack | — |
| **utterance** | 1 ประโยค/1 ช่วงพูดในบทประชุม (จาก .vtt) ถูกทำให้เป็น record หน้าตาเดียวกับ Slack ทุกโมดูลจึงใช้ต่อได้เลยไม่ต้องเขียนใหม่ | บทประชุม standup = 9 utterance ในตัวอย่าง |
| **pasted chat / แชทที่วาง** | บทสนทนาที่คน copy ออกจากแอป Slack แล้ววางเข้าระบบ ใช้กับห้องที่ token ดึงไม่ถึง — DM, กลุ่มส่วนตัว, workspace อื่น ระบบอ่านรูปแบบ `ชื่อ  [2:21 PM]` ที่คลิปบอร์ดให้มาโดยตรง | `tam/ingest/slack_paste.py` · source = `slack_paste` · **ไม่มี thread_ts** เพราะสกรอลล์ที่ copy มาไม่ใช่เธรด (`6 replies` คือหลักฐานว่า reply ไม่ได้ถูก copy มา) · id เป็น hash ของเนื้อหา วางทับกันได้ |
| **thread / thread_ts** | เธรดของ Slack และ timestamp ที่ใช้เป็นรหัสเธรด สำคัญเพราะ "อยู่เธรดเดียวกัน" คือ **ground truth** ไม่ใช่การเดา | ทั้งประชุมมี thread_ts เดียว จึงต้องถ่วงน้ำหนักคนละแบบกับเธรด Slack |
| **ground truth** | ความจริงที่รู้แน่ ไม่ได้มาจากโมเดล ใช้เป็นไม้บรรทัดวัดโมเดล | เธรด Slack, ผู้พูด, เวลา |
| **ingest** | ขั้นดูดข้อมูลเข้า → `export_slack` (ดึงจาก Slack), `prepare_messages` (ล้าง), `meetings` (บทประชุม), `notes` (โน้ตที่พิมพ์เอง), `slack_paste` (แชทที่ copy มาวาง) | `tam/ingest/` |
| **clean / normalize** | ล้าง markup ของ Slack, ตัด bot, ตัด `<@U…>`, รวม quote ให้เป็นข้อความอ่านได้ | 23 → 18 ข้อความในตัวอย่าง |
| **merge-into** | รวมข้อมูลใหม่ **เข้า** ไฟล์เดิม ไม่ทับ ถ้าใช้ `--out` ทับไฟล์ที่มีบทประชุมอยู่ ระบบจะปฏิเสธและบอกว่าควรใช้ flag ไหน | `--merge-into data/processed/messages.json` |
| **held-out** | ส่วนที่กันไว้ไม่ให้โมเดลเห็นตอนเทรน เอาไว้วัดตอนหลัง ถ้าไม่กัน ตัวเลขจะสวยเพราะจำได้ ไม่ใช่เพราะเข้าใจ | กันไว้ **24 thread** — และกันเป็น thread ไม่ใช่เป็นข้อความ |
| **split by thread** | วิธีแบ่ง train/test ที่ถูกสำหรับข้อมูลบทสนทนา ถ้าแบ่งตามข้อความ ครึ่งบทสนทนาเดียวกันจะไปอยู่ทั้งสองฝั่ง = โกงตัวเอง | `split_by_thread()` ใน `finetune.py` |
| **synthetic** | ข้อมูลที่แต่งขึ้น ไม่ใช่ของจริง ใช้ทดสอบกลไกได้ ใช้สรุปเรื่องภาษาที่ทีมใช้จริงไม่ได้ | `synthetic_work_chat.json` 1,000 แถว |
| **fixture** | คำตอบ API ที่บันทึกไว้ ใช้ demo/test แบบไม่ต้องต่อของจริง | `fixtures/*.json`, `ledger.fixture.json` |
| **gitignore** | ไฟล์ที่ห้ามขึ้น git | export จริง, embedding cache, `.env`, น้ำหนักโมเดล — ที่ commit คือโค้ด + ข้อมูลสังเคราะห์ |

## 2. Embedding — หัวใจของการค้นหาเชิงความหมาย

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **embedding / vector** | เปลี่ยนข้อความเป็นตัวเลขชุดหนึ่ง ข้อความที่ความหมายใกล้กันจะได้ตัวเลขที่อยู่ใกล้กัน นี่คือเหตุผลที่ค้นด้วย "คำไม่ตรง" แล้วยังเจอ | 1 record → เวกเตอร์ 1,024 ตัวเลข |
| **dimension (dim)** | ความยาวของเวกเตอร์ ยาวกว่าไม่ได้แปลว่าดีกว่าเสมอ | bge-m3 = **1024**, MiniLM = 384 |
| **embedding model / encoder** | โมเดลที่ทำหน้าที่แปลงข้อความเป็นเวกเตอร์ | ค่า default = **`BAAI/bge-m3`** (568M พารามิเตอร์, รันบน CPU, ในเครื่อง) |
| **checkpoint / pretrained** | โมเดลสำเร็จรูปที่คนอื่นเทรนมาแล้ว โหลดมาใช้ได้เลย | โหลดจาก Hugging Face |
| **multilingual** | โมเดลที่รองรับหลายภาษาใน **vector space เดียวกัน** ไทยกับอังกฤษความหมายเดียวกันจึงอยู่ใกล้กันได้โดยไม่ต้องแปล | จำเป็น เพราะทีมพิมพ์ปนกันในประโยคเดียว |
| **cross-lingual** | ความสามารถข้ามภาษา — ถามไทย เจออังกฤษ | วัดแล้วยังไม่สมบูรณ์: query ไทย/อังกฤษปน หา record อังกฤษได้ 0.84 แต่หา record ไทยที่ความหมายเดียวกันได้ 0.66 (เปลี่ยนมา bge-m3 ช่องว่างแคบจาก 0.49 → **0.18**) |
| **token / word piece** | ชิ้นย่อยที่โมเดลตัดข้อความออกเป็น ไม่ใช่คำ ไม่ใช่ตัวอักษร ใช้นับความยาวที่โมเดลรับได้ | — |
| **context length** | จำนวน token สูงสุดที่โมเดลอ่านได้ เกินจากนั้น **ตัดทิ้งแบบเงียบ ๆ** ไม่มี error | MiniLM = 128 → ตัดทิ้ง **13.4%** ของ record จริง (22,916 token) · bge-m3 = **8192** → ไม่มีปัญหานี้ |
| **truncation** | การถูกตัดข้อความทิ้งเพราะยาวเกิน context | ตัวที่ยาวที่สุดคือ thread รวมและ standup template = ตัวที่สำคัญที่สุดต่อการจัดกลุ่ม |
| **cosine similarity** | วัดว่าเวกเตอร์สองตัวชี้ไปทางเดียวกันแค่ไหน 1.00 = ทางเดียวกัน ค่าที่เห็นบ่อยคือ 0.3–1.0 | **ห้ามพูดว่าเป็น "ความมั่นใจ" หรือ "%"** เป็นค่าเทียบกันเองเท่านั้น |
| **L2-normalise** | ปรับทุกเวกเตอร์ให้ยาว 1 ผลคือ Euclidean distance และ dot product ให้ **ลำดับเดียวกับ cosine เป๊ะ ๆ** — เปลี่ยนไปใช้ตัวอื่นคือไม่เกิดอะไรขึ้นเลย | ตอบคำถาม "ทำไมไม่ลองวัดระยะแบบอื่น" ได้ด้วยประโยคนี้ |
| **embedding cache** | เก็บเวกเตอร์ที่คำนวณแล้วไว้ รอบต่อไปคำนวณแค่ข้อความใหม่/ที่แก้ | key = `sha256(ข้อความ)` เท่านั้น ไม่มีชื่อคน เวลา ช่อง · เก็บเป็น `.npz` แยกไฟล์ต่อโมเดล |
| **fp32 / น้ำหนักโมเดล** | ไฟล์โมเดลที่ต้องโหลดลงเครื่อง | bge-m3 = **2.1 GB** (+ reranker อีก 2.1 GB) เทียบ MiniLM 458 MB |
| **CPU / MPS** | รันด้วย CPU หรือชิปกราฟิกของ Mac | ทั้งหมดรันบน CPU ได้ ไม่ต้องมี GPU |

## 3. ปัญหาของ vector space (คำที่ทำให้ดูรู้ลึก)

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **anisotropy** | เวกเตอร์ที่โมเดลพ่นออกมากองอยู่ในกรวยแคบ ๆ ผลคือข้อความที่ไม่เกี่ยวกันเลยก็ได้ cosine ~0.8 ไปแล้ว เหลือที่ให้แยกน้อย | นี่คือสาเหตุที่ "ตั้งเลขเส้นแบ่ง" ไม่เวิร์ก |
| **space transform** | วิธีแก้ anisotropy — `center` ลบค่ากลางของ corpus, `abtt` (all-but-the-top) ตัดองค์ประกอบหลักที่ครอบงำออก, `whiten` ปรับสเกลทุกแกน | ลองแล้ว **corpus เล็กเกินจะตัดสิน** ปิดไว้เป็น default |
| **rank-deficient** | corpus เล็กกว่าจำนวน dimension → เมทริกซ์ความแปรปรวนไม่มีข้อมูลพอ | `whiten` บน 33 record ทำให้ spread = **0.000** พอดี ทุกคู่เหมือนกันหมด (มี warning เตือนแล้ว) |
| **hubness** | มีข้อความบางอันอยู่ใกล้ทุกอย่าง เลยถูกดึงขึ้นมาทุก query เช่น "มีอัปเดตมั้ย" | แก้ด้วย **CSLS** = หักความหนาแน่นของเพื่อนบ้านตัวเองออก (preset `dense-csls`) |
| **spread** | โมเดลใช้ช่วง 0–1 กว้างแค่ไหน แคบ = ตัดสินกันที่ทศนิยมตำแหน่งที่สาม | e5 = 0.035 (แคบสุด) · MiniLM = 0.146 · bge-m3 = 0.090 |
| **thread separation** | `(cosine เฉลี่ยในเธรดเดียวกัน − ต่างเธรด) / sd(ต่างเธรด)` — วัดจากทุกคู่ ไม่ใช่จาก query ไม่กี่อัน จึงเชื่อถือได้กว่า | e5-large 1.85 > bge-m3 1.71 > e5-base 1.55 > MiniLM 1.49 > mpnet 1.25 |

## 4. Retrieval — ทำไมไม่ใช้ cosine ตัวเดียว

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **retrieval** | ขั้นดึงของที่เกี่ยวข้องขึ้นมา (คนละเรื่องกับการจัดกลุ่ม) | `tam/retrieval/` |
| **dense** | ค้นด้วยความหมายผ่าน embedding | จับ paraphrase ข้ามภาษาได้ แต่ตาบอดเรื่องรหัสตรง ๆ |
| **lexical / sparse** | ค้นด้วยคำที่ตรงกันจริง ๆ | จับ `REV-1421`, `getUserProfile`, error code — พวกนี้เกือบเป็นหลักฐานว่าเป็นงานชิ้นเดียวกัน |
| **BM25** | สูตรมาตรฐานของการให้คะแนนคำตรง คำหายากมีน้ำหนักมาก คำที่โผล่ทุกที่มีน้ำหนักน้อย | **query ที่ไม่มีคำร่วมกับ corpus เลยได้ 0.000 พอดี** — คุณสมบัตินี้คือหัวใจของ relevance gate (§11) |
| **IDF** | น้ำหนัก "คำนี้หายากแค่ไหนใน corpus" | ใช้ทั้งใน BM25 และใน anchor |
| **tokenisation (ภาษาไทย)** | ตัดคำ — ปัญหาคือ **ไทยไม่เว้นวรรค** | ใช้ **PyThaiNLP `newmm`** ถ้ามี ไม่มีก็ใช้ n-gram ตัวอักษรซ้อนกัน |
| **n-gram / character trigram** | ตัดเป็นชิ้นตัวอักษร 3 ตัวซ้อนกัน วิธีหยาบแต่ไม่ต้องพึ่งพจนานุกรม | เป็นวิธีที่บอทใช้ตอนไม่ได้ต่อ pipeline — และเป็นเหตุผลว่าทำไมโหมดต่อ pipeline ดีกว่า |
| **anchor** | สตริงเป็นรูปธรรมที่สองข้อความใช้ร่วมกัน (รหัสตั๋ว ชื่อระบบ ชื่อบริษัท) ถ่วงด้วย IDF และวัดแบบสมมาตร | ใช้ทั้งค้นหาและ **ตั้งชื่อคลัสเตอร์** |
| **structural signals** | สัญญาณที่ Slack ให้ฟรี — อยู่เธรดเดียวกัน, เวลาใกล้กัน, คนเดียวกันพูด | "fix แล้ว กำลัง deploy" ไม่มีเนื้อหาหัวข้อเลย สิ่งที่บอกได้คือเวลา |
| **hybrid** | รวม dense + BM25 | ใน README เรียกว่า "คุ้มที่สุดต่อจำนวนบรรทัดโค้ด" |
| **fusion** | วิธีรวมคะแนนจากหลายสัญญาณที่สเกลไม่เท่ากัน | default = RRF, ทางเลือก = z-score |
| **RRF (Reciprocal Rank Fusion)** | รวม **ลำดับ** ไม่ใช่รวมคะแนน เพราะแต่ละสัญญาณสเกลคนละเรื่อง (e5 อัดทุกอย่างไว้ 0.80–1.00 ถ้าเฉลี่ยคะแนนดิบมันจะครอบงำ) | ผลข้างเคียงที่ต้องรู้: **คะแนน RRF ของอันดับ 1 เท่ากันทุก query** — `Android` กับ query ขยะได้ `0.032786883413791656` เท่ากันเป๊ะทุกหลัก |
| **z-score** | รวมแบบรักษาขนาดคะแนนไว้ | ใช้เมื่ออยากได้ magnitude |
| **cross-encoder / rerank** | อ่าน query กับข้อความ **พร้อมกัน** ในรอบเดียว แม่นกว่ามาก แต่ index ล่วงหน้าไม่ได้ จึงทำได้แค่บน top 50 | เป็นสเตจเดียวที่แยก "API พร้อมแล้ว" จาก "รอ API อยู่" ได้ — คำเกือบเหมือนกัน ความหมายตรงข้าม เวกเตอร์แทบเท่ากัน |
| **top-k** | เอามากี่อันดับ | default 10 · rerank ทำบน 50 |
| **preset** | ชุดสเตจที่ตั้งชื่อไว้ ใช้ค้น/วัด/พล็อตด้วยชุดเดียวกัน | `dense` `lexical` `hybrid` `hybrid-anchors` `hybrid-rerank` `full` `related` |
| **`--explain`** | พิมพ์ว่าแต่ละสเตจให้คะแนนเท่าไหร่ และคำไหน/anchor ไหนตรงจริง | `why: dense=1.00 bm25=1.00 anchors=1.00 cross=0.99` |
| **min-max normalise** | ปรับคะแนนให้อยู่ 0–1 **เทียบกันเองในผลชุดนั้น** | จึงบอกได้แค่ "อันนี้เทียบกับเพื่อนในลิสต์" ไม่ได้บอกว่า "เกี่ยวจริงไหม" |

## 5. ตัวเลขวัดผล (metric) — อย่าพูดเลขที่ไม่รู้ว่าวัดอะไร

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **nDCG@k** | ดูว่าของที่ควรอยู่บนอยู่บนจริงไหม ใน k อันดับแรก ให้เครดิตตำแหน่งด้วย 1.0 = สมบูรณ์แบบ | `nDCG@3 0.84`, `nDCG@10 0.89` บนตัวอย่างที่ commit |
| **MRR** | 1/อันดับของคำตอบถูกอันแรก | 1.00 = คำตอบถูกอยู่อันดับ 1 ทุก query |
| **MAP** | ค่าเฉลี่ยความแม่นทุกตำแหน่งที่มีของถูก | 0.79–0.86 |
| **recall@k** | ของที่ควรเจอ เจอกี่ % ใน k อันดับแรก | — |
| **triplet accuracy** | ให้ข้อความหนึ่ง โมเดลบอกได้ไหมว่า "เพื่อนในเธรดเดียวกันใกล้กว่าคนแปลกหน้า" — **50% = เดาสุ่ม** | bge-m3 = **63.7%** (ตัวเดิม MiniLM 59.4%) |
| **baseline** | ตัวเทียบพื้น ถ้าชนะไม่ได้ก็ไม่ต้องทำ | MiniLM คือ baseline หลังเปลี่ยน default |
| **label set / eval file** | ไฟล์ที่คนติดป้ายไว้ว่า query นี้คำตอบคือ id ไหน | มีแค่ **4 query** → nDCG แยกโมเดลไม่ออก ต่างกันไม่เกิน 0.01 = ข้อความ 1 อันสลับที่ นี่คือข้อค้นพบเรื่อง **label set ไม่พอ** ไม่ใช่เรื่องโมเดล |
| **weak labels** | สร้างป้ายกำกับอัตโนมัติจากโครงสร้าง (เช่นเธรด) แทนการติดมือ | `evaluation/weak_labels.py` |

## 6. การจัดกลุ่ม — จาก "ข้อความ" เป็น "งาน 1 ชิ้น"

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **clustering** | จัดข้อความเป็นกอง ต่างจาก ranking: ranking ตอบ "อะไรใกล้อันนี้" clustering ตอบ "ในช่องนี้มีเรื่องอะไรอยู่บ้าง" | คำถามหลังตอบด้วยเส้นแบ่งคะแนนคู่ ๆ ไม่ได้ |
| **graph / node / edge** | ทำข้อความเป็นจุด ความเกี่ยวข้องเป็นเส้น | 33 จุด 93 เส้น ในตัวอย่างที่วัด |
| **edge weight** | น้ำหนักของเส้น รวมจาก cosine + เธรด + เวลาใกล้ + anchor ร่วม | `EdgeWeights` มีน้ำหนัก **`meeting_thread` แยกและต่ำกว่าเธรด Slack มาก** เพราะประชุมเดียวมีหลายเรื่อง ถ้าถ่วงเท่ากันประชุมทั้งอันยุบเป็นก้อนเดียว |
| **community detection / Louvain** | อัลกอริทึมหากลุ่มก้อนในกราฟ ไม่ต้องบอกล่วงหน้าว่าจะมีกี่กลุ่ม (ต่างจาก k-means) | `analysis/graph.py` |
| **resolution** | ปุ่มปรับว่าให้กลุ่มละเอียดหรือหยาบ | ปรับ 1.0 → 6.0 แล้ว blocked ยังได้ 2 เท่าเดิม = ยืนยันว่าปัญหาไม่ได้อยู่ที่การจัดกลุ่ม |
| **modularity** | คุณภาพการแบ่งกลุ่มในตัวมันเอง > 0.30 ถือว่ามีโครงสร้างจริง | **0.587** |
| **ARI / NMI** | เทียบกลุ่มที่ได้กับ ground truth (เธรด Slack) ที่ระบบไม่เคยถูกบอก | ARI **0.463** · NMI **0.689** |
| **work item** | **หน่วยของโปรดักต์นี้** = งาน 1 ชิ้น = กองข้อความ 5–15 ข้อความ ข้าม Slack และห้องประชุม "บั๊กหน้าโปรไฟล์แอนดรอยด์" คือ 1 การ์ด ไม่ใช่ 10 ข้อความ | หน่วยไม่ใช่ message และไม่ใช่ channel — ประโยคนี้พูดตอนเปิดได้เลย |
| **item_id** | รหัสงานที่คงที่ข้ามการ rebuild (รหัสตั๋ว หรือ hash เช่น `c30a929`) | ต่างจาก **cluster rank** (เลข 1,2,3) ที่ใช้ได้แต่จะเปลี่ยนตัวหลัง rebuild |
| **linker** | ตัวตัดสินว่าข้อความไปอยู่งานชิ้นไหน ลำดับความสำคัญ: รหัสตั๋ว > เธรด > มติของคลัสเตอร์ และทุกการเชื่อมบอกหลักฐานของตัวเอง | `analysis/linker.py` · คนแก้ทับได้ เขียนลงไฟล์ที่ linker อ่าน |
| **label (ของคลัสเตอร์)** | ชื่อกอง = anchor ที่สมาชิกใช้ร่วมกันอย่างมีเอกลักษณ์ที่สุด **ไม่มีโมเดลเขียน** | ตัวพิมพ์เล็ก คั่นด้วย comma เช่น `omega, usd, agentforce add` · ถ้าไม่มีของร่วมกันเลยจะขึ้น `(no shared anchor)` |

## 7. ความสัมพันธ์และสถานะ — จุดที่ขายจริง

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **typed relation** | ความสัมพันธ์ที่ **มีชนิดและมีทิศ** — cosine ทำแบบนี้ไม่ได้ เพราะ `sim(A,B) == sim(B,A)` มันบอกได้แค่ "เกี่ยว" ไม่เคยบอกได้ว่า "เกี่ยวยังไง" | ประโยคนี้คือคำตอบว่าทำไมไม่หยุดที่ semantic search |
| **relation types** | `resolves` (แก้ให้) · `blocked_by` (ติดเพราะ) · `duplicates` (ซ้ำ) · `answers` (ตอบ) · `follows_up` (ตาม/ทวง) · `same_topic` | ข้อความก่อนหน้าชี้ไปหาข้อความหลัง เพราะในแชทคนที่ตอบ/แก้คือคนที่พูดทีหลัง |
| **cue phrase / cue** | วลีชี้สัญญาณที่ระบบใช้ตัดสิน เช่น `เสร็จแล้ว` `ยังรอ` `blocked` `waiting for` | ทุกการตัดสินใจ **บอกได้ว่ามาจาก cue คำไหน** → ผิดแล้วแก้ได้ ไม่ใช่ผิดแบบไม่รู้สาเหตุ |
| **rules vs NLI** | `--method rules` = ใช้ cue + ลำดับเวลา อธิบายได้ · `--method nli` = ใช้ NLI cross-encoder จับ paraphrase ที่ cue พลาด แต่อธิบายอะไรไม่ได้นอกจากเลข | ค่า default = rules |
| **NLI** | natural language inference — ตัดสินว่าประโยค B เป็นจริงตามประโยค A ไหม | ใช้เป็นทางเลือกในการ type relation |
| **state** | สถานะงาน: `blocked` / `resolved` / `active` **คำนวณด้วยกฎบน typed relation ไม่เคยผ่านโมเดลภาษา** | คำโฆษณาผิดคือเสียหน้า **สถานะผิดคือ standup พัง** จึงไม่ให้โมเดลแตะ |
| **evidence / evidence_id** | เหตุผลที่คนอ่านได้ + id ของข้อความที่พิสูจน์ | `"blocked since 2026-08-14 16:31 — cue "ยังรอ""` + id — กดถึงข้อความนั้นได้ใน 1 คลิก |
| **provenance** | สาวกลับไปหาต้นตอได้ | ในเอกสารออกแบบเขียนว่า "provenance คือฟีเจอร์" ไม่ใช่ของแถม |
| **citation** | id ข้อความที่คำสรุปอ้างถึง | โมเดลเขียนได้ แต่ **โค้ดตรวจทุกอัน** id ที่ไม่อยู่ในงานชิ้นนั้นถูกทิ้ง |
| **unverified** | สรุปที่ citation ไม่รอดการตรวจเลยแม้แต่อันเดียว → ขึ้นป้ายเตือนบนหน้าจอ | โมเดลแต่งประโยคมั่นใจ ๆ ได้ แต่แต่ง id ที่มีอยู่จริงใน corpus ไม่ได้ |
| **derived vs generated** | **derived** = คำนวณมา (state, ผู้เกี่ยวข้อง, แหล่ง, timeline, หลักฐาน) · **generated** = โมเดลเขียน (แค่ประโยคสรุป) | หัวใจของการนำเสนอ: ส่วนที่เชื่อได้คือส่วนที่คำนวณ ส่วนที่โมเดลเขียนคือส่วนที่เล็กที่สุด |
| **summarizer backend** | `template` (default, ไม่ใช้โมเดล ไม่ออกเน็ต) หรือ `claude` (เรียก API) | สลับด้วย env var `SUMMARIZER=` |
| **digest** | สรุปว่าในหน้าต่างเวลานี้อะไรขยับ เรียง blocked ก่อน | `analysis/digest.py`, หน้า `/` |
| **window (--days)** | ช่วงเวลาที่ digest มอง | default 7 วัน · ตัวอย่างที่ commit ต้องใช้ `--days 3650` เพราะ export ลงวันที่ 2025-08-01 |
| **blockers** | หน้าที่กรองเฉพาะ `blocked` เรียงตามติดนานสุด | ว่างบ่อย และ **ว่างคือข่าวดี** ต้องออกแบบให้ไม่เหมือน error |
| **timeline** | แถวเหตุการณ์: `เมื่อไหร่ · ความสัมพันธ์ · จากข้อความ → ไปข้อความ` เป็นห่วงโซ่เหตุ-ผล ไม่ใช่ feed | 1–6 แถวต่องาน |
| **drift** | งานที่ Slack บอกอย่าง ระบบตั๋วบอกอีกอย่าง | **ของจริงแล้ว** — ต่อ YouTrack (อ่านอย่างเดียว) 197 ใบ เปิดค้าง 57 · `analysis/drift.py` → `/tracker`, `/api/tracker`, `/meowtam drift` · วัดได้ **3 ใบที่สถานะขัดกัน** และ **24 ใบเงียบเกิน 21 วัน** · ข้อจำกัดที่ยังอยู่: ประโยคที่ตัดสินสถานะกับประโยคที่พิมพ์เลขทิกเก็ต **ไม่ใช่อันเดียวกันเลย (0 จาก 3)** การ์ดจึงโชว์สองประโยคและติดป้ายเตือน |
| **decision log / supersession** | บันทึกมติ และการที่มติใหม่ **ลบล้าง** มติเก่า | เขียนเมื่อมีคนบันทึกมติจริง |

## 8. การเทรนโมเดลเอง (fine-tuning) — และทำไมมันแพ้

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **fine-tune** | เอาโมเดลสำเร็จรูปมาเทรนต่อด้วยข้อมูลของเราเอง | ทำ 2 รอบ **แพ้ทั้ง 2 รอบ** น้ำหนักลบไปแล้ว (คืนพื้นที่ 932 MB) |
| **base model** | โมเดลตั้งต้นที่เอามาเทรนต่อ | ทั้งสองรอบเริ่มจาก MiniLM → ติด context 128 มาด้วย บทเรียนคือถ้าจะทำอีกต้องเริ่มจาก bge-m3 |
| **positive / negative pair** | คู่ที่ควรใกล้ / คู่ที่ควรไกล | positive = สองข้อความในเธรดเดียวกัน ไม่ต้องติดป้ายมือ |
| **MultipleNegativesRankingLoss** | loss ที่ใช้ตัวอื่นใน batch เป็น negative อัตโนมัติ | 2,984 คู่ (synthetic) / 2,661 คู่ (จริง) |
| **epoch / batch size** | วนข้อมูลกี่รอบ / ป้อนทีละกี่ตัว | 2 epoch, batch 32, ~152 วินาทีบน CPU |
| **loss** | ตัวเลขความผิดพลาดตอนเทรน ลดลง = เรียนอยู่ (แต่ไม่ได้แปลว่าใช้งานได้ดีขึ้น) | 5.151 → 2.839 **แล้วก็ยังแพ้** — ประโยคนี้ดีสำหรับตอบคำถาม |
| **memorisation / overfit** | จำข้อมูลที่เห็นมา ไม่ได้เข้าใจ | all-pairs ดูดี 0.64 แต่บน held-out เหลือ 0.33 → ครึ่งหนึ่งของกำไรคือการจำ |
| **floor 200 คู่** | เกณฑ์ขั้นต่ำที่เครื่องมือปฏิเสธไม่เทรนถ้าไม่ถึง | ต่ำกว่านั้นคือ fit noise · ตัวอย่างที่ commit ได้ 8 คู่, export 33 ข้อความได้ 45 คู่ |
| **LoRA** | เทรนเฉพาะอะแดปเตอร์เล็ก ๆ ไม่ขยับน้ำหนักทั้งโมเดล | โมเดลบางตัวในแคตตาล็อกใช้ (jina-v3) |
| **trust_remote_code** | ยอมให้รันโค้ดที่มาพร้อมโมเดลจากอินเทอร์เน็ต — เป็นความเสี่ยงด้านความปลอดภัย | 2 โมเดลในแคตตาล็อกต้องใช้ และ **1 ตัวพังจริงบน transformers 5.x** (ตรวจแล้ว ไม่ได้เดา) |
| **ข้อสรุปที่ต้องพูดให้ตรง** | corpus ~900 ข้อความ / 24 held-out thread **เล็กเกินกว่าจะชนะโมเดลสำเร็จรูป** และ fine-tune ทั้งสองทำให้ **relevance gate แย่ลง** (ขยะได้ cosine 0.96–0.97) | "ถ้ามันไม่ชนะโมเดลฐาน แปลว่า corpus เล็กเกิน — นั่นคือข้อมูล ไม่ใช่ความล้มเหลว" |

## 10. ภาษาไทยและ NLP — จุดที่คนฟังจะประทับใจ

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **word segmentation** | ตัดคำ — ไทยไม่มีช่องว่างระหว่างคำ ทุกอย่างที่สมมติว่ามีช่องว่างจะพังเงียบ ๆ | ใช้ PyThaiNLP `newmm` |
| **substring vs token match** | หาแบบ "มีตัวอักษรชุดนี้อยู่ในสตริง" กับ "มี token คำนี้จริง" | `รอ` แบบ substring เจอ 92 ครั้ง เกือบทั้งหมดผิด เพราะอยู่ใน "ร**อบ**" "ก**รอก**" "ห**รอ**" เช่นเดียวกับ `ติด` ที่อยู่ใน "ติดต่อ ติดตั้ง ติดตาม" — **ทางแก้คือตัดคำแล้วแมตช์ระดับ token** |
| **จาก 0 blocked เป็น 7** | เคยรายงาน 37 active · 19 resolved · **0 blocked** บน 936 ข้อความ · วันนี้หน้าต่าง 7 วันได้ 22 active · **7 blocked** · 9 resolved จาก 38 งาน | เหตุเดิมคือ cue ที่ระบบใช้ (`ยังรอ` `ติดที่` `blocked`) เจอ **0 ครั้ง** ขณะที่ทีมใช้ `pending` (15) และ `ค้าง` (4) → คอขวดคือ **ระดับของสัญญาณ ไม่ใช่ลิสต์คำ** · แก้ด้วยการอ่าน cue ทีละ**บรรทัด** (`ingest/blockers.py` + `quoted.asserted_lines()`) ไม่ใช่เติมคำเข้าลิสต์ |
| **กับดักที่ห้ามเติมมั่ว** | `blocker` 14 จาก 22 ครั้งมาจาก **template standup** ที่ขึ้นหัวว่า "Any blockers?" — เติมเป็น cue แล้วมันจะ fire ทุกโพสต์ | สิ่งที่ระบบทำถูกคือ **รายงาน 0 ตรง ๆ ไม่แต่งงานติดขึ้นมาให้ดูดี** |

## 11. Relevance gate — เรื่องที่ต้องเล่าให้ได้ (ไฮไลต์ทางเทคนิค)

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **relevance gate** | ด่านตัดสินว่า "มีอะไรตรงมั้ย ถ้าไม่มี ต้องกล้าตอบว่าไม่มี" | ถ้าไม่มีด่านนี้ ระบบจะตอบทุกคำถามด้วยข้อความอะไรก็ได้ที่ใกล้ที่สุด |
| **threshold / floor** | เส้นแบ่งค่าคงที่ เช่น "cosine ต้อง ≥ 0.45" | **กลไกนี้ผิดตั้งแต่ต้น** ไม่ใช่โมเดลไม่ดี |
| **ทำไมผิด** | `max cosine` เหนือ N เอกสาร **สูงขึ้นตาม N สำหรับ query อะไรก็ตาม** มี 1,102 เอกสารยังไงก็มีอันที่ดูคล้าย | ทดสอบ 5 โมเดล **ไม่มีตัวไหนหา floor ที่แยกได้** → กรองขยะได้ 0/5 |
| **absolute vs relative** | absolute = เทียบกับอะไรก็ได้ (BM25 ดิบ, cosine ดิบ) · relative = เทียบกันเองในผลชุดนั้น (RRF score, `why`) | ตอบ "เกี่ยวจริงไหม" ได้เฉพาะ absolute |
| **กลไกใหม่: 2 สัญญาณ ต้องผ่านทั้งคู่** | `lexical` = BM25 ดิบของ record ที่ดีสุด ต้อง **> 0** · `dense` = cosine ดิบของ record ที่ใกล้สุด ต้อง **≥ TAM_MIN_COSINE** | BM25 จับ **ขยะ** ได้เพราะขยะไม่มีคำร่วมกับ corpus เลย → 0.000 · dense ยังต้องมี เพื่อจับ **คำถามจริงที่ใช้คำต่างจาก corpus** |
| **ผลที่วัดได้** | ขยะถูกกรอง **4 จาก 5** · query จริง **ไม่เสียเลย 0 จาก 12** | ของเดิม cosine floor: กรองขยะได้ 0/5 |
| **ตัวที่ยังหลุด (พูดออกไปเลย)** | `ๆๆๆ ฯฯฯ ฤฤฤ ฅฅฅ` ผ่านด่าน เพราะ `ๆ` และ `ฯ` เป็นอักขระไทยจริงที่มีใน corpus จึงมีคำตรงกันจริง | เป็น **ขอบเขตของกลไก ไม่ใช่ bug** และคงไว้ในลิสต์ทดสอบตั้งใจ — การตรวจที่เงียบ ๆ ตัดตัวนี้ออกจะรายงานว่าผ่านหมดทั้งที่รูยังอยู่ |
| **calibration** | การหาค่าที่ถูกสำหรับ corpus ตรงหน้า | `check-api` **วัดใหม่ทุกที่ที่รัน** ไม่เชื่อเลขที่พิมพ์ไว้ใน README |
| **corpus size ไม่ใช่ตัวแปร** | เคยเชื่อว่า corpus เล็ก = ขยะได้คะแนนสูง **ผิด** | สุ่มย่อย 25→936 record ขยะขยับแค่ 0.870→0.918 (แบน) แต่ corpus **ต่างเนื้อหา** ขนาดใกล้กันขยับ 0.581/0.767/0.918 → **เนื้อหากำหนด ไม่ใช่ขนาด** |
| **fail loud** | pipeline เก่าที่ไม่ส่ง `relevance` มา → บอท **throw ทิ้ง** ไม่ปล่อยผ่าน | ด่านที่เงียบ ๆ เลิกทำงานคือความล้มเหลวที่กลไกนี้มีอยู่เพื่อป้องกัน |
| **`--strict-gate`** | ให้ผล calibration มีผลต่อ exit code สำหรับ CI | ปกติ calibration พิมพ์แต่ไม่ทำให้ fail (exit 0 พร้อม `⚠ 3/4`) |

## 12. ระบบและสถาปัตยกรรม

| คำ | หมายถึง | ในโปรเจกต์นี้ |
|---|---|---|
| **pipeline** | สายพานประมวลผล: ดูด → ล้าง → embed → ค้น → จัดกลุ่ม → หาความสัมพันธ์ → สรุป | ฝั่ง Python |
| **CLI** | สั่งงานผ่านบรรทัดคำสั่ง | 22 จาก 25 โมดูลตอบ `--help` ได้ |
| **FastAPI** | เว็บเฟรมเวิร์ก Python เสิร์ฟทั้ง HTML และ JSON จาก digest ก้อนเดียวกัน | ไม่มี build step ไม่มี `node_modules` ไม่มี frontend แยกให้ต้องคอย sync |
| **endpoint / JSON API** | ที่อยู่ที่เรียกเอาข้อมูลได้ | อ่าน 8 ตัว: `/api/digest` `/api/blockers` `/api/item/{key}` `/api/search` `/api/people` `/api/person/{user}` `/api/tracker` `/api/health` · เขียน 3 ตัวที่ต้องมี token: `POST /api/reindex` `POST /upload` `POST /upload/notes` · หน้า HTML 8 หน้าอ่านข้อมูลชุดเดียวกัน |
| **loopback bind** | เปิดให้เข้าถึงได้แค่จากเครื่องตัวเอง | ถ้าจะเปิดออกเน็ตต้องใส่ `--expose` **และ** ต้องตั้ง `TAM_ADMIN_TOKEN` เพราะ `/upload` กับ `/api/reindex` เขียนข้อมูล |
| **reindex / rebuild** | อ่าน record ใหม่แล้วสร้าง index ใหม่ ไม่ต้อง restart | หลังอัปโหลดบทประชุม ใช้เวลา 5–60 วินาที และ API ตอบ **503** ระหว่างนั้น |
| **cache warm/cold start** | รอบแรกช้าเพราะต้อง embed ทั้ง corpus รอบต่อไปเป็นวินาที | `Reused 27 cached embedding(s)` |
| **env var / `.env`** | ค่าตั้งที่อยู่นอกโค้ด | `EMBEDDING_MODEL` `SUMMARIZER` `TAM_API_URL` `TAM_MIN_COSINE` `TAM_ADMIN_TOKEN` `HF_HUB_OFFLINE` |
| **venv** | สภาพแวดล้อม Python แยกของโปรเจกต์ | สร้างด้วย Python 3.10 (ของ Homebrew) เพราะ ML wheel รองรับดีกว่า |
| **seam / fallback** | รอยต่อระหว่างสองฝั่ง และพฤติกรรมเมื่อฝั่งหนึ่งล่ม | ตั้ง `TAM_API_URL` แล้ว **ไม่มี fallback** — pipeline ตอบไม่ได้ บอทไม่ยอมสตาร์ต ดีกว่าเสิร์ฟข้อมูลเก่าที่หน้าตาเหมือนของสด |
