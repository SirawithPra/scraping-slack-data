05ต่างจากต่อ AI เข้า Slack ตรง ๆ ยังไง

เริ่มจากยอมรับก่อนว่าอะไรไม่ใช่จุดต่าง — 936 ข้อความใส่ context ของโมเดลใหญ่ได้สบาย “ข้อมูลเยอะเกิน” ไม่ใช่จุดขาย และเรื่องเข้าใจภาษาไทย โมเดลใหญ่เหนือกว่าตัวที่เราใช้ชัดเจน

  1. กล้าตอบว่า “ไม่มี” — รายงาน 0 blocked จาก 936 ข้อความ ทั้งที่เป็นฟีเจอร์เรือธง ถามโมเดลว่า “อะไรติด” จะได้คำตอบที่ฟังดูดีทุกครั้ง และไม่มีทางรู้ว่าอันไหนจริง
  2. ทุกคำกล่าวอ้างมี citation ที่ตรวจในโค้ด — ไม่ใช่ในคำสัญญา อ้างผิดจะถูกตัดและติดป้ายให้เห็น
  3. คนแก้แล้วมันจำ — และรอด rebuild เพราะชื่องานผูกกับเนื้อหา ไม่ใช่เลขคลัสเตอร์ที่เปลี่ยนทุกครั้ง
  4. ข้อมูลไม่ออกจากเครื่อง — โมเดลรันในเครื่อง ต้องตั้งค่าเองถึงจะมีอะไรถูกส่งออก
  5. ทำซ้ำได้ — input เดิมให้ผลเดิม ตรวจย้อนได้ว่าทำไมถึงสรุปแบบนั้น

ข้อสรุปเชิงสถาปัตยกรรมคือ ใช้ทั้งคู่ — กฎกับ retrieval ถือสถานะและหลักฐานเพราะต้อง audit ได้ ส่วนโมเดลภาษาเขียนประโยค เพราะภาษาดีกว่า และ citation ถูกตรวจอยู่แล้ว

06ข้อกังวลที่ต้องพูดตรง ๆ

1 · จับ blocker ได้น้อยกว่าที่มีจริงมาก และคอขวดไม่ใช่คำศัพท์

อ่านด้วยมือทั้ง 76 ข้อความที่เข้าข่าย พบ blocker จริง 22 ข้อความ แต่ถ้าใส่ตัวตรวจที่แม่น 100% ทั้ง precision และ recall ผลออกมาได้แค่ 2 งาน เพราะ topic เป็นคลัสเตอร์แนวเรื่อง กินเวลา median 43 วัน 25 ข้อความ แล้วคำ ack สั้น ๆ คำเดียวตัดสินคลัสเตอร์ 44 ข้อความข้ามหลายสัปดาห์ได้ งานรอบถัดไปอยู่ที่การจัดกลุ่มและกฎตัดสินสถานะ ไม่ใช่ที่ลิสต์คำ

2 · ข้อมูลลูกค้าอยู่ในเนื้อข้อความ

ในข้อมูลจริงมีอีเมลลูกค้าและเลขตัวถังรถถูกพิมพ์อยู่ในข้อความ โหมดชื่อสมมุติซ่อนแค่ชื่อคนส่ง ไม่ได้ซ่อนสิ่งเหล่านี้ ก่อนแคปหน้าจอไปนำเสนอต้องไล่ดูด้วยตาทุกครั้ง

3 · ตัวกรองยังหลุดคำค้นภาษาจริงที่ไม่มีเรื่องนั้นในคลัง

พบตอนสาธิต ไม่ใช่ตอนวัด — คำสามัญคำเดียวที่บังเอิญตรงก็ผ่านประตูได้ มีตัวเลือกที่วัดแล้วให้ margin เป็นบวกครั้งแรก แต่ยังไม่ลง เพราะเป็นตัวอย่าง 11 อันที่ผู้พัฒนาเลือกเอง — จะเชื่อได้ต้องมีชุดที่คนอื่นเขียนหรือคำค้นจริงจาก log

4 · ตัวอย่างที่แจกมาสาธิตการรวมข้ามที่มาไม่ได้อีกแล้ว

โมเดลใหม่เลิกรวมบทประชุมกับแชทเข้าด้วยกันบนไฟล์ตัวอย่าง — และตรวจแล้วว่า สิ่งที่โมเดลเก่ารวมนั้นผิด มันเอาประโยคทักทายภาษาไทย 5 ประโยค (รวมบรรทัดปิดประชุม) มากองกัน โดยระบบเองตั้งชื่อกลุ่มนั้นไม่ได้ ตัวอย่างจึงไม่เคยมีเคสจริงอยู่ในนั้น ต้องเติมเข้าไป — รอการตัดสินใจ

5 · git history ยังมีชื่อบริษัทและ Slack ID จริง

tip สะอาดแล้ว แต่ commit ก่อนหน้ายังมีอยู่ การลบต้อง rewrite history + force push บน public repo ซึ่งทำลายของถาวรและพัง clone ของคนอื่น — รอการตัดสินใจ

6 · ยังไม่ได้ต่อ ticket system จึงยังไม่มี drift detection

การเทียบว่า “Slack บอกอย่าง ticket บอกอีกอย่าง” เป็นจุดต่างที่แรงที่สุดในแนวคิด และยังไม่มีแหล่งข้อมูล ระบบจึงแสดงว่าว่าง ไม่ใช่แสดงตัวอย่างปลอม

07พัฒนาต่อ — เรียงตามผลกระทบที่วัดได้

ลำดับนี้มาจากการวัด ไม่ใช่จากความรู้สึก
ลำดับทำอะไรทำไมอยู่ตำแหน่งนี้
1ล้าง markup ก่อนแมตช์ cue ตอนนี้ cue ไปแมตช์ในบล็อกโค้ดที่คนแปะรีวิวมา ในข้อความที่ขีดฆ่าแล้ว และในเอกสารเงื่อนไขที่กิน 5.5% ของคลัง · บอทกับ AI assistant 39 ข้อความ (27.9% ของตัวอักษร) ไม่ถูกแยกออก — ประเมินว่าได้ผลมากกว่าการแก้ cue ทั้งหมดรวมกัน
2ประตูกันไม่ให้ ack คำเดียวตัดสินคลัสเตอร์ทั้งก้อน คือคอขวดที่วัดแล้วว่ากั้น 20 จาก 22 blocker ไว้ · ต้องมีเงื่อนไขน้ำหนัก/ที่มาว่าอะไรมีสิทธิเปลี่ยนสถานะ และคิดสถานะระดับงานย่อย
3จัดกลุ่มให้ละเอียดขึ้น ขึ้น resolution เป็น 4.0 ทำให้เพดานที่ทำได้ขยับจาก 2 เป็น 4 งาน · ต้องวัดว่ามันไม่แตกงานจริงออกเป็นเสี่ยง
4ตัวกรองแบบวัดความครอบคลุมของคำถาม ตัวเดียวที่วัดได้ margin เป็นบวก · ต้องมีชุดทดสอบที่คนอื่นเขียนก่อนจะเชื่อ
5ต่อ YouTrack / Notion ปลดล็อก drift detection ซึ่งเป็นจุดต่างเชิงแนวคิดที่แรงสุด และเป็นสิ่งที่ต่อ AI เข้า Slack ทำแทนไม่ได้
6เปิดตารางเวลาอัตโนมัติ “ไม่ต้องถามก็รู้” คือหัวใจ · โค้ดมีแล้วแต่ปิดอยู่ ควรเปิดหลังข้อ 1–2 เพราะไม่อยากส่งวาระที่เต็มไปด้วยของเก่า
7เทรนโมเดลอีกครั้ง เมื่อ ข้อมูลมากพอ อยู่ท้ายสุดเพราะวัดแล้วว่าแพ้ · ถ้าจะกลับมาทำ ต้องได้ข้อมูลหลายเท่า และเปลี่ยนฐานเป็น bge-m3 ก่อน ไม่ใช่เทรนบนตัวเดิม
