# ใช้งานจริงวันต่อวัน

เอกสารนี้ตอบคำถามเดียว: **ตื่นมาแล้วต้องพิมพ์อะไร** ไม่ใช่การติดตั้ง (นั่นอยู่ใน
[USER_MANUAL.md](USER_MANUAL.md)) และไม่ใช่เหตุผลเชิงออกแบบ (นั่นอยู่ใน
[../pipeline/README.md](../pipeline/README.md))

คำสั่งทุกบรรทัดตรวจกับโค้ดแล้ว **Python รันจาก `pipeline/` · npm รันจาก `slack-bot/`**

## ก่อนอื่น: ทำให้ชื่อคนอ่านออก

ค่าเริ่มต้นระบบเห็นคนเป็น `U0EXAMPLE12` เพราะ Slack ส่งมาแบบนั้น ดึงชื่อจริงครั้งเดียว:

```bash
python3 -m tam.ingest.users --fetch      # ต้องมี SLACK_TOKEN ที่มี scope users:read
```

เขียนลง `data/user_names.json` (gitignore แล้ว — ชื่อคนคือข้อมูลส่วนบุคคล)
**ไม่ต้อง reindex** เพราะการแปลชื่อเกิดตอนแสดงผล ไม่ได้เก็บลงข้อมูล

**ไฟล์นี้ไฟล์เดียวคือคำตอบว่าใครคือใคร** — ทั้ง dashboard และ Slack bot อ่านไฟล์เดียวกัน
(`slack-bot/src/names.ts` ใช้สูตรเดียวกับฝั่ง Python) ชื่อคนคนหนึ่งจึงตรงกันทุกหน้าจอ
ตัวข้อมูลที่เก็บยังเป็น id เหมือนเดิม ชื่อเป็นแค่การแสดงผล — ของจริงที่ push ขึ้น git
จึงไม่มีชื่อใครอยู่เลย

```bash
python3 -m tam.ingest.users --check --records data/processed/<ไฟล์>.json
#   → id ที่ยังไม่มีชื่อ (พวกนี้จะแสดงเป็น "ชื่อสมมุติ" ที่อ่านเหมือนชื่อจริง)
python3 -m tam.ingest.users --set U0123ABCDE=ชื่อที่อยากให้แสดง
#   → คนที่ Slack ไม่คืนมาให้ (ลาออก / guest ต่าง workspace / bot ที่ยิงผ่าน webhook)
#     --fetch รอบหน้าจะไม่ลบทิ้ง
```

| อยากได้อะไร | ตั้งค่า |
|---|---|
| ชื่อจริง (ทีมอ่านของตัวเอง) | ไม่ต้องตั้ง — ใช้ทันทีเมื่อมีไฟล์ |
| **ชื่อสมมุติ (เดโม / แคปหน้าจอ / เล่าให้คนนอกฟัง)** | `TAM_NAMES=pseudonym` |
| id ดิบ (ไล่บั๊กว่า join ถูกไหม) | `TAM_NAMES=id` |

> **ตั้งให้ตรงกันทั้งสองฝั่ง** — `pipeline/.env` กับ `slack-bot/.env` ใช้ตัวแปรชื่อเดียวกัน
> ถ้าตั้งไม่เหมือนกัน เว็บกับ Slack จะเรียกคนเดียวกันไม่เหมือนกัน ซึ่งแย่กว่าเรียกเป็น id ทั้งคู่
> ฝั่ง bot ถ้าเป็น `pseudonym` จะไม่ mention จริง (`<@U0…>`) ด้วย เพราะ Slack จะไปดึงชื่อจริง
> มาแสดงเองตอนเรนเดอร์ — แคปหน้าจอไปก็มีชื่อจริงติดไปอยู่ดี

ชื่อสมมุติคงที่ต่อคน — `U0EXAMPLE12` เป็น `แก้ม ม.` ทุกครั้งทุกเครื่อง บทสนทนาจึงยังอ่าน
เป็นบทสนทนา แต่ไม่ระบุตัวใครได้

> **⚠️ ก่อนแคปหน้าจอไปใส่สไลด์** `TAM_NAMES=pseudonym` ซ่อนแค่**ชื่อคนส่ง** ไม่ได้ซ่อน
> ข้อมูลที่ถูกพิมพ์อยู่ในเนื้อข้อความ — ในข้อมูลจริงที่ทดสอบมีอีเมลลูกค้าและเลขตัวถังรถ
> อยู่ในข้อความ ต้องไล่ดูด้วยตาก่อนทุกครั้ง

## จังหวะที่ 1 — เช้าก่อน standup (2 นาที)

**สิ่งที่อยากรู้:** เมื่อวานมีอะไรขยับ อะไรติด และใครควรถูกถาม

```bash
# terminal ค้างไว้ตัวเดียว รันทีเดียวทั้งวัน
python3 -m tam.web.server --records data/processed/messages.json --days 7 --port 8899
```

เปิด <http://localhost:8899> แล้วอ่านสามหน้าตามลำดับนี้:

| หน้า | อ่านเพื่ออะไร |
|---|---|
| `/blockers` | **เปิดอันนี้ก่อน** งานที่ติด เรียงติดนานสุดขึ้นก่อน แต่ละอันมีข้อความที่พิสูจน์ |
| `/` | ทุกงานที่ขยับในหน้าต่าง 7 วัน พร้อมสถานะและคนเกี่ยวข้อง |
| `/item/<id>` | กดจากสองหน้าบน — timeline ของงานชิ้นเดียวข้าม Slack กับที่ประชุม |

ถ้าไม่อยากเปิดเบราว์เซอร์:

```bash
python3 -m tam.analysis.digest --records data/processed/messages.json --blockers
```

**อ่านผลอย่างไรให้ถูก** ทุกบรรทัดสถานะมี "หลักฐาน" ต่อท้าย เช่น
`blocked since 2026-08-14 16:31 — cue "ยังรอ"` — นั่นคือ**ข้อความจริงที่ทำให้ระบบสรุปแบบนั้น**
กดเข้าไปดูได้ ถ้าอ่านแล้วไม่เห็นด้วย ระบบผิด ไม่ใช่คุณผิด (ดูจังหวะที่ 4)

**ถ้าขึ้นว่าไม่มีอะไรติด** นั่นคือคำตอบจริง ไม่ใช่ระบบพัง — สถานะมาจาก typed relation
ระบบไม่แต่งงานติดขึ้นมาเพื่อให้หน้าจอดูมีอะไร

## จังหวะที่ 2 — ตอนประชุม / จดประชุม

**สิ่งที่อยากได้:** บันทึกประชุมกลายเป็นส่วนหนึ่งของงานเดียวกับที่คุยใน Slack ไม่ใช่ไฟล์แยก

### วิธีที่ใช้จริงบ่อยสุด — วางโน้ตที่จดเอง

ส่วนใหญ่ไม่มีไฟล์ถอดเสียง มีแค่โน้ตที่คนจดแล้วเอาไปโพสต์ใน Slack — **วางลงไปได้เลย**

1. เปิด <http://localhost:8899/upload>
2. วางโน้ตในกล่องบนสุด · ใส่เรื่อง/คนจด/เวลา (ไม่ใส่ก็ได้)
3. กดส่ง — รวมเข้า corpus แล้ว rebuild ให้เอง

```bash
# หรือจาก terminal / clipboard
pbpaste | python3 -m tam.ingest.notes --title "Sprint planning"           --author U08H0UD5R36 --merge-into data/processed/real_all.json
```

**สองอย่างที่ควรรู้**

- **วางหนึ่งครั้ง = หนึ่ง record** ไม่ได้แยกเป็นบรรทัด เพราะโน้ตที่โพสต์ลง Slack ก็คือข้อความเดียว
  และบรรทัดถูกอ่านอยู่แล้วข้างใน — บรรทัดแบบ `• Pending Mild - list all field` จะขึ้นใน `/blockers`
  **พร้อมอ้างบรรทัดนั้นเป็นหลักฐาน** ไม่ใช่อ้างโน้ตทั้งก้อน
- **วางข้อความเดิมซ้ำในวันเดียวกัน = แทนที่ของเดิม** (id มาจากเนื้อหา) แก้แล้ววางใหม่ได้ ไม่เกิดของซ้ำ
  ที่มาแย่งอันดับกันเองในผลค้นหา · เปลี่ยนแค่ชื่อเรื่องไม่ทำให้กลายเป็นโน้ตใหม่

### ถ้ามีไฟล์ถอดเสียง

ระบบรับ **`.vtt` และ `.srt`** ซึ่งคือสิ่งที่ Zoom / Google Meet / Teams ส่งออกให้อยู่แล้ว
(Meet: เปิด "Transcripts" ไว้ · Zoom: Cloud Recording → Audio transcript)

1. เปิด <http://localhost:8899/upload> แล้วใช้ฟอร์ม**ล่าง**
2. ลากไฟล์ transcript ใส่ · ใส่ชื่อประชุม · เวลาที่เริ่ม
3. กดส่ง — ระบบรวมเข้า corpus แล้ว rebuild ให้เอง

**หรือทาง command line:**

```bash
python3 -m tam.ingest.meetings \
        --transcript ~/Downloads/standup-2026-08-18.vtt \
        --title "Daily standup 18 ส.ค." \
        --started 2026-08-18T09:30 \
        --merge-into data/processed/messages.json
```

`--started` เป็นเวลาที่ประชุมเริ่ม ใส่แบบไม่มี timezone ได้ (ระบบถือว่าเป็นเวลาเครื่องคุณ)
`--merge-into` รวมเข้าไฟล์ที่มีอยู่ **ไม่ทับทิ้ง** และถ้าอัปโหลดไฟล์เดิมซ้ำ มันแทนที่ของรอบก่อน
ไม่ใช่เพิ่มซ้ำสองรอบ

**หลังรวมแล้วได้อะไร** งานชิ้นเดียวจะมีทั้งข้อความ Slack และบทประชุมอยู่ด้วยกัน — ดูคอลัมน์
"ที่มา" บนการ์ด (`💬 8 · 🎙 2` = 8 จาก Slack, 2 จากที่ประชุม) นี่คือสิ่งที่ Slack เพียว ๆ
บอกไม่ได้: **"เรื่องนี้คุยจบในห้องประชุมแล้ว ไม่ได้หายไป"**

> ผู้พูดในบทประชุมมาเป็น**ชื่อ** ไม่ใช่ Slack id ระบบจึง DM คนนั้นไม่ได้ และมันจะบอกตรง ๆ
> ว่า DM ไม่ได้กี่คน แทนที่จะเดาว่าชื่อนี้คือใครแล้วส่งผิดคน

**รีเฟรช Slack ทุกเช้า — คำสั่งเดียว**

```bash
python3 -m tam.ingest.daily
```

ทำครบสามขั้นตามลำดับ: ดึงเฉพาะที่ใหม่จาก**ทุกช่องที่บอทถูกเชิญเข้า** → merge เข้า corpus →
สั่ง dashboard rebuild · **วัดแล้ว 16 วินาที** สำหรับ 5 ช่อง / 37 ข้อความใหม่

```bash
python3 -m tam.ingest.daily --dry-run    # ดูว่าจะทำอะไร โดยไม่เรียก Slack เพิ่ม
```

`--dry-run` มีเพราะ rate limit ~1 request/นาที — คำถามว่า "มันจะทำอะไร" ต้องตอบได้
โดยไม่ต้องจ่าย budget ไปหาคำตอบ

สิ่งที่มันคิดเผื่อไว้:

- **เช้าที่ไม่มีใครคุย = ไม่แตะ corpus** ไม่ใช่ error และไม่ re-embed ให้เปล่าประโยชน์
- **ล้มขั้นไหนหยุดทันที** ดีกว่าได้ corpus ที่มีบางช่องใหม่บางช่องเก่าแล้ว digest ดูเหมือนครบ
- **ไม่มี dashboard รันอยู่ก็ไม่ล้ม** แต่จะบอกว่าข้าม rebuild และบอกคำสั่งให้สั่งเอง
- **ข้ามข้อความที่บอทโพสต์เอง** เพราะบอทโพสต์ digest ลงช่องที่ตัวเองอ่าน ถ้าไม่ข้าม
  ข้อความ digest จะไปจับกลุ่มกับงานที่มันบรรยายอยู่ แล้วเสริมตัวเองทุกรอบ
  (เจอจริง 5 โพสต์ก่อนจะจับได้ · บอทอื่นเก็บไว้ เพราะแจ้ง deploy คือเหตุการณ์จริง)

## จังหวะที่ 2.5 — เจอเรื่องค้างในแชทส่วนตัว

**สิ่งที่อยากได้:** เรื่องที่คุยกันใน DM หรือกลุ่มส่วนตัวแล้ว "มันค้างอยู่" ก็ควรโผล่ใน
`/blockers` เหมือนกัน ไม่ใช่หายไปเพราะห้องนั้น export ไม่ถึง

bot token อ่านได้เฉพาะห้องที่เชิญมันเข้าไป ห้องที่เหลือมีทางเดียวคือ **ลากเลือก → copy → วาง**

1. เปิด <http://localhost:8899/upload> → กล่อง **"หรือ copy แชทจาก Slack มาวาง"**
2. วางที่ copy มา · ใส่ว่าคุยที่ไหน (เช่น `DM พี่ Natta`) · วันแรกของบทสนทนา
3. กด **ดูก่อนว่าอ่านถูกไหม** → ตารางบอกว่าอ่านได้กี่ข้อความ ใครพูดอะไรตอนไหน
   และมีอะไรที่อ่านไม่ออกบ้าง — **ยังไม่เขียนอะไรลง corpus จนกว่าจะกดยืนยัน**

```bash
# หรือจาก clipboard — --dry-run คือดูเฉย ๆ ไม่เขียนอะไร
pbpaste | python3 -m tam.ingest.slack_paste --title "DM พี่ Natta" --date 2026-08-19 --dry-run
```

**สี่อย่างที่ควรรู้**

- **หนึ่งข้อความ Slack = หนึ่งข้อความในระบบ** (ต่างจากโน้ตที่วางทั้งก้อนเป็นอันเดียว) แต่ที่คน
  เดียวกันพิมพ์รัวติดกันใน 2 นาทีจะถูกต่อเป็น record เดียว เพราะ `ของผมสุดท้ายคือแตก` แล้วต่อ
  `400` คือประโยคเดียวที่กด Enter คั่น — และ `400` เดี่ยว ๆ ไม่มีอะไรให้จัดกลุ่มเลย
- **ของแถมที่ Slack copy ติดมาถูกตัดให้เอง** — `6 replies`, ชื่อไฟล์รูปที่เชื่อมติดหน้าชื่อคน,
  `(edited)`, แถวรีแอ็กชัน · ส่วนวงเล็บเหลี่ยมที่ไม่ใช่เวลา เช่น `[BUG][View redemption result]`
  **ยังอยู่ในเนื้อความ** ไม่ถูกอ่านเป็นเวลา
- **วางทับกันได้** วางสกรอลล์ที่คาบกับของเดิม ข้อความซ้ำจะถูกแทนที่ ไม่เพิ่มซ้ำ — ไม่ต้องจำว่า
  วางไปถึงไหนแล้ว
- **ที่มาจะขึ้นว่า "แชทที่วาง" (📋) ไม่ใช่ "Slack"** และไม่มีลิงก์กลับไปข้อความต้นฉบับ เพราะที่
  copy มาไม่มี id ของ Slack ติดมาด้วย — ข้อความที่ export มาคือของเต็ม ที่วางคือเท่าที่คนเลือก

## จังหวะที่ 3 — ใน Slack ระหว่างวัน

เปิดบอทค้างไว้ (ต่อจาก pipeline ตัวเดิม ไม่ตัดสินใจเอง):

```bash
cd slack-bot
TAM_API_URL=http://127.0.0.1:8899 npm start
```

พิมพ์ในช่องไหนก็ได้ที่เชิญบอทเข้าไปแล้ว:

| พิมพ์ | ได้อะไร |
|---|---|
| `/meowtam` | งานที่คุณเกี่ยวข้อง |
| **`/meowtam daily`** | **ฟอร์ม daily — เห็นคนเดียว** ก๊อปไปกรอกแล้ววางในเธรดของโพสต์ daily |
| `/meowtam daily post` | โพสต์ daily ของวันนี้เดี๋ยวนี้ (ปกติยิงเองตอน 09:00) |
| `/meowtam daily summary` | อ่านเธรดแล้วสรุปเดี๋ยวนี้ (ปกติยิงเองตอน 10:45) |
| `/meowtam blocked` | เฉพาะที่ติด (`block` ก็ได้) |
| `/meowtam digest` | digest เต็ม (`standup` ก็ได้) |
| `/meowtam recall <ข้อความ>` | ค้นด้วยความหมาย — วางประโยคที่จำไม่ได้ว่าใครพูดไว้ที่ไหน |
| `/meowtam <TICKET-123>` | เปิดงานนั้นพร้อม timeline |
| `/meowtam @someone` | งานของคนนั้น |
| **`/meowtam silent`** | **ticket ที่เปิดค้างและไม่มีใครแตะเกิน 21 วัน** (`quiet` ก็ได้) |
| `/meowtam drift` | ที่ Slack กับ ticket ไม่ตรงกัน (ปิด ticket แล้วยังคุย / คุยว่าติดแต่ ticket ยังเปิด) |
| **`/meowtam format`** | **รูปแบบที่ระบบอ่านได้ — ส่งให้ทีมดูได้เลย** (`help` / `template` ก็ได้) |
| `/meowtam reload` | อ่านข้อมูลใหม่โดยไม่ต้อง restart (ใช้ตอนเดโม) |
| `/mt …` | ย่อของทุกอันข้างบน |

**`recall` คือตัวที่ใช้บ่อยที่สุดจริง ๆ** — "เรื่อง pricing ที่คุยกันอาทิตย์ก่อนสรุปว่าอะไร"
วางลงไปเลย มันหาข้อความต้นทางให้ พร้อมบอกว่า**ทำไม**อันนี้ตรง (`dense 0.91 · bm25 1.00`)

**ถ้าไม่มีอะไรตรงจริง มันจะบอกว่าไม่มี** ไม่ใช่เดาห้าอันมาให้ดูดี — เพราะมันเช็คสองชั้น
(ต้องมีคำตรงกัน **และ** ความหมายใกล้) ข้อจำกัดที่รู้อยู่: ตัวอักษรไทยซ้ำ ๆ อย่าง `ๆๆๆ ฯฯฯ`
ยังหลุดได้ เพราะมันเป็นอักขระที่มีอยู่จริงในข้อความ

## จังหวะที่ 3.2 — daily thread (โพสต์เช้า ตอบในเธรด สรุป 10:45)

**สิ่งที่อยากได้:** standup ที่ยังคุยกันใน Slack เหมือนเดิม แต่ของเมื่อวานไม่หายไป

ทุกเช้าบอทโพสต์หัวข้อเดียวลงช่อง:

```
Daily as of 20 August 2026
ตอบในเธรดของข้อความนี้ได้เลย — พิมพ์ /meowtam daily แล้วผมส่งฟอร์มให้ (เห็นคนเดียว)
```

ใต้โพสต์นั้นจะมี **ลิงก์กลับไปเธรดของเมื่อวาน** (กดแล้วกระโดดไปเลย) และ
**บรรทัด Pending ของเมื่อวานที่ยังไม่หาย พร้อมแท็กคนที่รออยู่** — ไม่ต้องเลื่อนหาเอง

คนในทีมพิมพ์ `/meowtam daily` เพื่อรับฟอร์ม (Slack แสดงให้คนที่พิมพ์คนเดียว):

```
Done Yesterday:
Finished ticket #[ID]

Focus Today:
Focus ticket #[ID]

Blockers / Pending:
Pending [เรื่องที่รออยู่] [@คนที่ต้องทำให้ก่อน หรือพิมพ์ PO ถ้ารอ PO ยืนยัน]
```

ก๊อปไปกรอกแล้ว **วางในเธรด** · ถ้าระบบเคยเห็นงานของคุณอยู่แล้ว ฟอร์มจะมีอีกกล่องที่
**กรอกมาให้แล้ว** ให้แก้แทนที่จะพิมพ์ใหม่

**หรือไม่ต้องพิมพ์เลย** — กดปุ่ม *ส่ง* ใน standup DM ตอน 08:45 ก็คือการตอบ daily ของวันนั้น
การ์ดนั้นมี **สามช่อง หัวข้อเดียวกับฟอร์มข้างบนเป๊ะ** (Done Yesterday / Focus Today /
Blockers / Pending) เติมมาให้แล้วจากงานของคุณ — ที่เติมมาเป็นตัวเดียวกับบล็อกสุดท้ายของ
`/meowtam daily` เพราะสองที่นี้เรียกฟังก์ชันเดียวกัน ไม่ใช่ของที่เขียนแยกกันแล้วบังเอิญคล้าย
และอ่านด้วย parser ตัวเดียวกัน

กดส่งแล้วบอทโพสต์เข้า**เธรด daily ทันที** ในนามของบอท (ไม่ปลอมเป็นคุณ) เพื่อนร่วมทีมจึงเห็น
เลยว่าคุณตอบอะไร ไม่ต้องรอสรุป 10:45 · ถ้ายังไม่ได้โพสต์ daily ของวันนั้น คำตอบรออยู่ก่อน
แล้วถูกยกเข้าเธรดตอนโพสต์ 09:00 เป็นข้อความแรกของเธรด

ในสรุป 10:45 บรรทัดของคนที่ตอบทาง DM ติดป้าย *(ตอบจาก standup DM)* ไว้ เพราะไม่มีข้อความ
ของตัวเองในเธรดให้กดดู · **ถ้าคนคนนั้นพิมพ์ในเธรดทีหลัง ของในเธรดชนะ** — เป็นคำพูดที่ใหม่กว่า
และเป็นสาธารณะกว่า
(กด *ข้ามวันนี้* = ไม่เก็บอะไรเลย ชื่อจะอยู่ฝั่ง "ยังไม่ตอบ" ในสรุป แต่ไม่มีใครถูกแท็กทวง)

**10:45 บอทอ่านเธรดนั้นแล้วสรุปในเธรดเดิม** — ใครตอบอะไร ติดอะไร รอใคร และ
**ใครยังไม่ตอบ** (นับจาก `STANDUP_USERS` เท่านั้น ไม่ใช่ทุกคนในช่อง)

**ห้าอย่างที่ควรรู้**

- **บรรทัด Pending เก็บไว้ตามที่พิมพ์** เพราะพรุ่งนี้มันจะถูกยกไปอ้างในช่องพร้อมแท็กคน —
  บอทสรุปคำของคุณใหม่แล้วแท็กคนอื่นให้ ถือเป็นการใส่คำในปากคุณ
- **แท็กได้แค่ที่คุณเขียนเอง** `@ชื่อ` หรือ `PO` · ไม่ได้เขียนก็ขึ้นว่า *ยังไม่ได้บอกว่ารอใคร*
  ไม่ใช่เดาเจ้าของให้
- **บรรทัดเดิมซ้ำ 3 รอบ = ประกาศในช่องและแท็กคนนั้น** นับเป็น "รอบของ daily" ไม่ใช่วันปฏิทิน —
  เสาร์อาทิตย์ไม่มีใครโพสต์ ไม่ได้แปลว่าเรื่องนั้นหายไป · เคลียร์แล้วก็ไม่ต้องใส่รอบถัดไป มันหายเอง
- **วางฟอร์มมาแต่ไม่กรอก (ยังมี `#[ID]` อยู่) ไม่นับว่าตอบ** และสรุปจะบอกแยกไว้ ไม่ใช่นับรวมว่าตอบแล้ว
- **กด *ส่ง* ใน DM ทั้งที่ไม่ได้กรอกอะไรเลย ก็ไม่นับว่าตอบ** — "ตอบว่าไม่มีอะไร" กับ "ยังไม่ตอบ"
  เป็นคนละเรื่อง และสรุปต้องแยกสองอย่างนี้ออกจากกันได้

ตอนเดโมไม่ต้องรอนาฬิกา: `/meowtam daily post` แล้ว `/meowtam daily summary`

## จังหวะที่ 3.5 — พิมพ์ให้ระบบอ่านได้ (คุ้มที่สุดต่อแรงที่ลง)

ทีมมี template standup อยู่แล้ว 4 หัวข้อ และ **ข้อความที่พิมพ์ใต้ `Are there any blockers?`
ถือเป็น blocker ตามที่เจ้าตัวบอกเอง** ระบบไม่ต้องเดาเลย

```
• What did accomplish yesterday?
ปิด ticket sorting แล้ว รอ QA
• What are you working on today?
ต่อหน้า profile
• Are there any blockers?
รอ requirement จาก ROPS ก่อน ถึงจะปรับ UI ต่อได้
• Others
-
```

**ทำไมคุ้ม** วัดจากข้อมูลจริง — มี 3 ครั้งที่คนเขียน blocker จริงในช่องนี้ และ
**cue list เดิมจับได้แค่ 1 ครั้ง** อีก 2 ครั้งเป็นประโยคธรรมดาที่ไม่มีคำไหนให้จับเลย
กรอกช่องนี้จึงให้หลักฐานที่คำค้นไปไม่ถึง

**สองอย่างที่ช่วยเพิ่ม**

- **ไม่มี blocker ก็เขียน `-` หรือ `None`** — "ตอบว่าไม่มี" ต่างจาก "ไม่ได้ตอบ" และระบบเชื่อคำตอบนั้น
  (จาก 18 โพสต์ที่ใช้ form มี 7 โพสต์ตอบว่าไม่มี)
- **ใส่รหัส ticket ถ้ามี** เช่น `PROJ-142` — linker ใช้เป็นชื่องานเอง ทำให้เรื่องเดียวกันไม่แตกเป็นหลายชิ้น

พิมพ์ `/meowtam format` ใน Slack เพื่อดูอันนี้ซ้ำ หรือส่งให้ทีมดู

> **ข้อจำกัดที่วัดแล้ว** บน corpus จริง blocker ที่คนประกาศเองทั้ง 3 อันอยู่ในงานชิ้นเดียวกัน
> และงานนั้นถูกแก้เสร็จ 2 เดือนหลังจากนั้น → **ผลต่อ digest วันนี้เป็นศูนย์**
> การอ่าน form ถูกต้องแล้ว แต่มันจะให้ผลเมื่อทีมเริ่มกรอกสม่ำเสมอ ไม่ใช่ย้อนหลัง

## จังหวะที่ 4 — ตอนระบบเข้าใจผิด (สำคัญที่สุด)

นี่คือจังหวะที่ต่างจากถาม AI แล้วจบไป **แก้แล้วมันจำ และรอบหน้าเปลี่ยนตาม**

**ถ้ามันจับข้อความไปผูกงานผิดชิ้น** — คลิกขวาที่ข้อความนั้นใน Slack → **ผูกกับ ticket**
→ เลือกงานที่ถูก

เขียนลง `pipeline/data/link_overrides.json` ซึ่ง linker อ่านเป็น **ชั้นสูงสุด ชนะทุกชั้น**
(สูงกว่า ticket key ที่เจอในข้อความ สูงกว่า thread สูงกว่าการจัดกลุ่มของโมเดล)
รอบ reindex ถัดไปงานจะถูกต้องตามที่คุณแก้ **และรอดข้าม rebuild** เพราะชื่องานผูกกับเนื้อหา
ไม่ใช่เลขคลัสเตอร์ที่เปลี่ยนทุกครั้ง

**สิ่งที่การกดเชื่อม *ไม่ได้* ทำ — อ่านตรงนี้ก่อนสรุปว่ามันพัง**

การเชื่อมบอกว่า *ข้อความนี้เป็นของงานไหน* แต่ **ไม่ได้ย้ายข้อความออกจากกลุ่ม**
ที่การจัดกลุ่มวางไว้ กลุ่มยังเป็นของ Louvain อยู่ ผลคือถ้าข้อความที่คุณเชื่อมไปนั่งอยู่คนละกลุ่ม
กับงานปลายทาง ตัวเลข “ข้อความ” ในหน้างานนั้นจะยังไม่นับมัน

วัดจากไฟล์จริงตอน 2026-08-20: เชื่อมไว้ 8 ครั้ง ตกถึงงานที่ตั้งใจ 2 ครั้ง
ที่เหลือคือข้อความอยู่คนละกลุ่ม หรือชี้ไปที่ข้อความที่ไม่มีใน corpus เลย

ทั้งสองกรณีตอนนี้ **มองเห็นได้ ไม่ต้องเดา**:

| ที่ | มันบอกอะไร |
|---|---|
| หน้างาน `/item/<ticket>` | หัวข้อ “เชื่อมไว้กับทิกเก็ตนี้ แต่ไปอยู่เรื่องอื่น” — พร้อมลิงก์ไปเรื่องที่มันไปอยู่จริง |
| หน้า `/tracker` | หัวข้อ “การกดเชื่อมที่ยังไม่มีผล” — ข้อความที่ pipeline หาไม่เจอ พร้อมสาเหตุ |
| หน้าจอตอนกดใน Slack | บอกว่าลงกี่ข้อความจากกี่ข้อความ และถ้าหาไม่เจอจะบอกว่าเพราะอะไร |
| `/api/health` | `unresolved_links` — จำนวนการเชื่อมที่ไม่มีผล สำหรับ monitor |

สาเหตุที่เจอบ่อยที่สุดคือ **ข้อความอยู่ใน channel ที่ตั้งค่าให้ข้าม** (`TAM_SKIP_CHANNELS`)
กดเชื่อมได้ตามปกติ แต่ไม่มีอะไรเกิดขึ้น เพราะ `read_records` ตัดข้อความนั้นทิ้งไปก่อนแล้ว

**และการค้นหารู้จักการเชื่อมแล้ว** — พิมพ์เลขทิกเก็ตในหน้า “ค้นหา” จะได้สองอย่าง:
งานชิ้นนั้นขึ้นมาเป็นการ์ดบนสุด (ไม่ต้องมีข้อความไหนพิมพ์เลขนั้นไว้เลยก็ได้)
และข้อความที่คนกดเชื่อมไว้จะค้นเจอด้วยเลขทิกเก็ต ทั้งที่ตัวข้อความไม่ได้พิมพ์เลขนั้น
บรรทัด “เจอได้เพราะมีคนกดเชื่อม…” จะบอกไว้ใต้ผลนั้น

**ถ้าที่ประชุมตกลงอะไรกันแล้ว** — คลิกขวาที่ข้อความสรุป → **บันทึกเป็นการตัดสินใจ**

เก็บลง decision log พร้อมเวลาของข้อความ (ไม่ใช่เวลาที่คุณกด) หาเจอด้วย `recall` ได้ตลอด
และถ้าตัดสินใจใหม่ทับอันเก่า มันโยงสองทางให้ ไล่ย้อนได้ว่าเปลี่ยนเพราะอะไร

## จังหวะที่ 5 — อัตโนมัติ (ถ้าอยาก)

```bash
# slack-bot/.env
ENABLE_SCHEDULE=1
DIGEST_CHANNEL=C…            # ช่องที่จะให้โพสต์ digest 09:25
STANDUP_USERS=U…,U…          # คนที่จะได้ standup draft ทาง DM 08:45 (กดส่งในการ์ด = ตอบ daily ของวันนั้น) · และเป็นรายชื่อที่ daily นับว่า "ยังไม่ตอบ"
TAM_SCHEDULE_TZ=Asia/Bangkok

DAILY_CHANNEL=C…             # ช่องของ daily thread (ว่างไว้ = ใช้ DIGEST_CHANNEL)
TAM_DAILY_AT=09:00           # โพสต์ "Daily as of …"
TAM_DAILY_SUMMARY_AT=10:45   # อ่านเธรดแล้วสรุปในเธรดนั้น
TAM_DAILY_PENDING_DAYS=3     # บรรทัด Pending เดิมซ้ำกี่รอบ ถึงจะประกาศในช่องและแท็กคน
```

**ตอนตั้งครั้งแรกให้ชี้ไปช่องทดสอบก่อน** ไม่ใช่ช่องงานจริง — ยิงผิดช่องแก้ไม่ได้
`ENABLE_SCHEDULE` ว่างไว้คือปิดทั้งหมด ปลอดภัยโดยค่าเริ่มต้น
