# ใช้งานจริงวันต่อวัน

เอกสารนี้ตอบคำถามเดียว: **ตื่นมาแล้วต้องพิมพ์อะไร** ไม่ใช่การติดตั้ง (นั่นอยู่ใน
[USER_MANUAL.md](USER_MANUAL.md)) และไม่ใช่เหตุผลเชิงออกแบบ (นั่นอยู่ใน
[../pipeline/README.md](../pipeline/README.md))

คำสั่งทุกบรรทัดตรวจกับโค้ดแล้ว **Python รันจาก `pipeline/` · npm รันจาก `slack-bot/`**

---

## ก่อนอื่น: ทำให้ชื่อคนอ่านออก

ค่าเริ่มต้นระบบเห็นคนเป็น `U0EXAMPLE12` เพราะ Slack ส่งมาแบบนั้น ดึงชื่อจริงครั้งเดียว:

```bash
python3 -m tam.ingest.users --fetch      # ต้องมี SLACK_TOKEN ที่มี scope users:read
```

เขียนลง `data/user_names.json` (gitignore แล้ว — ชื่อคนคือข้อมูลส่วนบุคคล)
**ไม่ต้อง reindex** เพราะการแปลชื่อเกิดตอนแสดงผล ไม่ได้เก็บลงข้อมูล

| อยากได้อะไร | ตั้งค่า |
|---|---|
| ชื่อจริง (ทีมอ่านของตัวเอง) | ไม่ต้องตั้ง — ใช้ทันทีเมื่อมีไฟล์ |
| **ชื่อสมมุติ (เดโม / แคปหน้าจอ / เล่าให้คนนอกฟัง)** | `TAM_NAMES=pseudonym` |
| id ดิบ (ไล่บั๊กว่า join ถูกไหม) | `TAM_NAMES=id` |

ชื่อสมมุติคงที่ต่อคน — `U0EXAMPLE12` เป็น `แก้ม ม.` ทุกครั้งทุกเครื่อง บทสนทนาจึงยังอ่าน
เป็นบทสนทนา แต่ไม่ระบุตัวใครได้

> **⚠️ ก่อนแคปหน้าจอไปใส่สไลด์** `TAM_NAMES=pseudonym` ซ่อนแค่**ชื่อคนส่ง** ไม่ได้ซ่อน
> ข้อมูลที่ถูกพิมพ์อยู่ในเนื้อข้อความ — ในข้อมูลจริงที่ทดสอบมีอีเมลลูกค้าและเลขตัวถังรถ
> อยู่ในข้อความ ต้องไล่ดูด้วยตาก่อนทุกครั้ง

## จังหวะที่ 1 — เช้าก่อน standup (2 นาที)

**สิ่งที่อยากรู้:** เมื่อวานมีอะไรขยับ อะไรติด และใครควรถูกถาม

```bash
# terminal ค้างไว้ตัวเดียว รันทีเดียวทั้งวัน
python3 -m tam.web.server --records data/processed/messages.json --days 7 --port 8899
```

เปิด <http://localhost:8899> แล้วอ่านสามหน้าตามลำดับนี้:

| หน้า | อ่านเพื่ออะไร |
|---|---|
| `/blockers` | **เปิดอันนี้ก่อน** งานที่ติด เรียงติดนานสุดขึ้นก่อน แต่ละอันมีข้อความที่พิสูจน์ |
| `/` | ทุกงานที่ขยับในหน้าต่าง 7 วัน พร้อมสถานะและคนเกี่ยวข้อง |
| `/item/<id>` | กดจากสองหน้าบน — timeline ของงานชิ้นเดียวข้าม Slack กับที่ประชุม |

ถ้าไม่อยากเปิดเบราว์เซอร์:

```bash
python3 -m tam.analysis.digest --records data/processed/messages.json --blockers
```

**อ่านผลอย่างไรให้ถูก** ทุกบรรทัดสถานะมี "หลักฐาน" ต่อท้าย เช่น
`blocked since 2026-08-14 16:31 — cue "ยังรอ"` — นั่นคือ**ข้อความจริงที่ทำให้ระบบสรุปแบบนั้น**
กดเข้าไปดูได้ ถ้าอ่านแล้วไม่เห็นด้วย ระบบผิด ไม่ใช่คุณผิด (ดูจังหวะที่ 4)

**ถ้าขึ้นว่าไม่มีอะไรติด** นั่นคือคำตอบจริง ไม่ใช่ระบบพัง — สถานะมาจาก typed relation
ระบบไม่แต่งงานติดขึ้นมาเพื่อให้หน้าจอดูมีอะไร

## จังหวะที่ 2 — ตอนประชุม / จดประชุม

**สิ่งที่อยากได้:** บันทึกประชุมกลายเป็นส่วนหนึ่งของงานเดียวกับที่คุยใน Slack ไม่ใช่ไฟล์แยก

ระบบรับ **`.vtt` และ `.srt`** ซึ่งคือสิ่งที่ Zoom / Google Meet / Teams ส่งออกให้อยู่แล้ว
(Meet: เปิด "Transcripts" ไว้ · Zoom: Cloud Recording → Audio transcript)

**วิธีที่ง่ายที่สุด — ลากไฟล์ใส่หน้าเว็บ:**

1. เปิด <http://localhost:8899/upload>
2. ลากไฟล์ transcript ใส่ · ใส่ชื่อประชุม · เวลาที่เริ่ม
3. กดส่ง — ระบบรวมเข้า corpus แล้ว rebuild ให้เอง

**หรือทาง command line:**

```bash
python3 -m tam.ingest.meetings \
        --transcript ~/Downloads/standup-2026-08-18.vtt \
        --title "Daily standup 18 ส.ค." \
        --started 2026-08-18T09:30 \
        --merge-into data/processed/messages.json
```

`--started` เป็นเวลาที่ประชุมเริ่ม ใส่แบบไม่มี timezone ได้ (ระบบถือว่าเป็นเวลาเครื่องคุณ)
`--merge-into` รวมเข้าไฟล์ที่มีอยู่ **ไม่ทับทิ้ง** และถ้าอัปโหลดไฟล์เดิมซ้ำ มันแทนที่ของรอบก่อน
ไม่ใช่เพิ่มซ้ำสองรอบ

**หลังรวมแล้วได้อะไร** งานชิ้นเดียวจะมีทั้งข้อความ Slack และบทประชุมอยู่ด้วยกัน — ดูคอลัมน์
"ที่มา" บนการ์ด (`💬 8 · 🎙 2` = 8 จาก Slack, 2 จากที่ประชุม) นี่คือสิ่งที่ Slack เพียว ๆ
บอกไม่ได้: **"เรื่องนี้คุยจบในห้องประชุมแล้ว ไม่ได้หายไป"**

> ผู้พูดในบทประชุมมาเป็น**ชื่อ** ไม่ใช่ Slack id ระบบจึง DM คนนั้นไม่ได้ และมันจะบอกตรง ๆ
> ว่า DM ไม่ได้กี่คน แทนที่จะเดาว่าชื่อนี้คือใครแล้วส่งผิดคน

**รีเฟรช Slack ทุกเช้า — คำสั่งเดียว**

```bash
python3 -m tam.ingest.daily
```

ทำครบสามขั้นตามลำดับ: ดึงเฉพาะที่ใหม่จาก**ทุกช่องที่บอทถูกเชิญเข้า** → merge เข้า corpus →
สั่ง dashboard rebuild · **วัดแล้ว 16 วินาที** สำหรับ 5 ช่อง / 37 ข้อความใหม่

```bash
python3 -m tam.ingest.daily --dry-run    # ดูว่าจะทำอะไร โดยไม่เรียก Slack เพิ่ม
```

`--dry-run` มีเพราะ rate limit ~1 request/นาที — คำถามว่า "มันจะทำอะไร" ต้องตอบได้
โดยไม่ต้องจ่าย budget ไปหาคำตอบ

สิ่งที่มันคิดเผื่อไว้:

- **เช้าที่ไม่มีใครคุย = ไม่แตะ corpus** ไม่ใช่ error และไม่ re-embed ให้เปล่าประโยชน์
- **ล้มขั้นไหนหยุดทันที** ดีกว่าได้ corpus ที่มีบางช่องใหม่บางช่องเก่าแล้ว digest ดูเหมือนครบ
- **ไม่มี dashboard รันอยู่ก็ไม่ล้ม** แต่จะบอกว่าข้าม rebuild และบอกคำสั่งให้สั่งเอง
- **ข้ามข้อความที่บอทโพสต์เอง** เพราะบอทโพสต์ digest ลงช่องที่ตัวเองอ่าน ถ้าไม่ข้าม
  ข้อความ digest จะไปจับกลุ่มกับงานที่มันบรรยายอยู่ แล้วเสริมตัวเองทุกรอบ
  (เจอจริง 5 โพสต์ก่อนจะจับได้ · บอทอื่นเก็บไว้ เพราะแจ้ง deploy คือเหตุการณ์จริง)

## จังหวะที่ 3 — ใน Slack ระหว่างวัน

เปิดบอทค้างไว้ (ต่อจาก pipeline ตัวเดิม ไม่ตัดสินใจเอง):

```bash
cd slack-bot
TAM_API_URL=http://127.0.0.1:8899 npm start
```

พิมพ์ในช่องไหนก็ได้ที่เชิญบอทเข้าไปแล้ว:

| พิมพ์ | ได้อะไร |
|---|---|
| `/meowtam` | งานที่คุณเกี่ยวข้อง |
| `/meowtam blocked` | เฉพาะที่ติด (`block` ก็ได้) |
| `/meowtam digest` | digest เต็ม (`standup` ก็ได้) |
| `/meowtam recall <ข้อความ>` | ค้นด้วยความหมาย — วางประโยคที่จำไม่ได้ว่าใครพูดไว้ที่ไหน |
| `/meowtam <TICKET-123>` | เปิดงานนั้นพร้อม timeline |
| `/meowtam @someone` | งานของคนนั้น |
| **`/meowtam format`** | **รูปแบบที่ระบบอ่านได้ — ส่งให้ทีมดูได้เลย** (`help` / `template` ก็ได้) |
| `/meowtam reload` | อ่านข้อมูลใหม่โดยไม่ต้อง restart (ใช้ตอนเดโม) |
| `/mt …` | ย่อของทุกอันข้างบน |

**`recall` คือตัวที่ใช้บ่อยที่สุดจริง ๆ** — "เรื่อง pricing ที่คุยกันอาทิตย์ก่อนสรุปว่าอะไร"
วางลงไปเลย มันหาข้อความต้นทางให้ พร้อมบอกว่า**ทำไม**อันนี้ตรง (`dense 0.91 · bm25 1.00`)

**ถ้าไม่มีอะไรตรงจริง มันจะบอกว่าไม่มี** ไม่ใช่เดาห้าอันมาให้ดูดี — เพราะมันเช็คสองชั้น
(ต้องมีคำตรงกัน **และ** ความหมายใกล้) ข้อจำกัดที่รู้อยู่: ตัวอักษรไทยซ้ำ ๆ อย่าง `ๆๆๆ ฯฯฯ`
ยังหลุดได้ เพราะมันเป็นอักขระที่มีอยู่จริงในข้อความ

## จังหวะที่ 3.5 — พิมพ์ให้ระบบอ่านได้ (คุ้มที่สุดต่อแรงที่ลง)

ทีมมี template standup อยู่แล้ว 4 หัวข้อ และ **ข้อความที่พิมพ์ใต้ `Are there any blockers?`
ถือเป็น blocker ตามที่เจ้าตัวบอกเอง** ระบบไม่ต้องเดาเลย

```
• What did accomplish yesterday?
ปิด ticket sorting แล้ว รอ QA
• What are you working on today?
ต่อหน้า profile
• Are there any blockers?
รอ requirement จาก ROPS ก่อน ถึงจะปรับ UI ต่อได้
• Others
-
```

**ทำไมคุ้ม** วัดจากข้อมูลจริง — มี 3 ครั้งที่คนเขียน blocker จริงในช่องนี้ และ
**cue list เดิมจับได้แค่ 1 ครั้ง** อีก 2 ครั้งเป็นประโยคธรรมดาที่ไม่มีคำไหนให้จับเลย
กรอกช่องนี้จึงให้หลักฐานที่คำค้นไปไม่ถึง

**สองอย่างที่ช่วยเพิ่ม**

- **ไม่มี blocker ก็เขียน `-` หรือ `None`** — "ตอบว่าไม่มี" ต่างจาก "ไม่ได้ตอบ" และระบบเชื่อคำตอบนั้น
  (จาก 18 โพสต์ที่ใช้ form มี 7 โพสต์ตอบว่าไม่มี)
- **ใส่รหัส ticket ถ้ามี** เช่น `PROJ-142` — linker ใช้เป็นชื่องานเอง ทำให้เรื่องเดียวกันไม่แตกเป็นหลายชิ้น

พิมพ์ `/meowtam format` ใน Slack เพื่อดูอันนี้ซ้ำ หรือส่งให้ทีมดู

> **ข้อจำกัดที่วัดแล้ว** บน corpus จริง blocker ที่คนประกาศเองทั้ง 3 อันอยู่ในงานชิ้นเดียวกัน
> และงานนั้นถูกแก้เสร็จ 2 เดือนหลังจากนั้น → **ผลต่อ digest วันนี้เป็นศูนย์**
> การอ่าน form ถูกต้องแล้ว แต่มันจะให้ผลเมื่อทีมเริ่มกรอกสม่ำเสมอ ไม่ใช่ย้อนหลัง

## จังหวะที่ 4 — ตอนระบบเข้าใจผิด (สำคัญที่สุด)

นี่คือจังหวะที่ต่างจากถาม AI แล้วจบไป **แก้แล้วมันจำ และรอบหน้าเปลี่ยนตาม**

**ถ้ามันจับข้อความไปผูกงานผิดชิ้น** — คลิกขวาที่ข้อความนั้นใน Slack → **ผูกกับ ticket**
→ เลือกงานที่ถูก

เขียนลง `pipeline/data/link_overrides.json` ซึ่ง linker อ่านเป็น **ชั้นสูงสุด ชนะทุกชั้น**
(สูงกว่า ticket key ที่เจอในข้อความ สูงกว่า thread สูงกว่าการจัดกลุ่มของโมเดล)
รอบ reindex ถัดไปงานจะถูกต้องตามที่คุณแก้ **และรอดข้าม rebuild** เพราะชื่องานผูกกับเนื้อหา
ไม่ใช่เลขคลัสเตอร์ที่เปลี่ยนทุกครั้ง

**ถ้าที่ประชุมตกลงอะไรกันแล้ว** — คลิกขวาที่ข้อความสรุป → **บันทึกเป็นการตัดสินใจ**

เก็บลง decision log พร้อมเวลาของข้อความ (ไม่ใช่เวลาที่คุณกด) หาเจอด้วย `recall` ได้ตลอด
และถ้าตัดสินใจใหม่ทับอันเก่า มันโยงสองทางให้ ไล่ย้อนได้ว่าเปลี่ยนเพราะอะไร

## จังหวะที่ 5 — อัตโนมัติ (ถ้าอยาก)

```bash
# slack-bot/.env
ENABLE_SCHEDULE=1
DIGEST_CHANNEL=C…            # ช่องที่จะให้โพสต์ digest 09:25
STANDUP_USERS=U…,U…          # คนที่จะได้ standup draft ทาง DM 08:45
TAM_SCHEDULE_TZ=Asia/Bangkok
```

**ตอนตั้งครั้งแรกให้ชี้ไปช่องทดสอบก่อน** ไม่ใช่ช่องงานจริง — ยิงผิดช่องแก้ไม่ได้
`ENABLE_SCHEDULE` ว่างไว้คือปิดทั้งหมด ปลอดภัยโดยค่าเริ่มต้น

| เมื่อไหร่ | ทำอะไร |

| ระหว่างวันใน Slack | `/meowtam recall …` |
| ตอนมันผิด | คลิกขวา → **ผูกกับ ticket** |

## ที่ยังทำไม่ได้ — พูดตรง ๆ

| อยากให้ทำ | สถานะ |
|---|---|
| ต่อ YouTrack / Notion | **ยังไม่ได้ต่อ** จึงยังไม่มี drift detection (เทียบ Slack กับ ticket) |
| เขียนกลับเข้า ticket | ยังไม่มี |
| DM คนที่พูดในที่ประชุม | ทำไม่ได้เมื่อ transcript ให้มาเป็นชื่อ ไม่ใช่ id — และมันจะไม่เดา |
| จับ blocker ได้ครบ | จับได้น้อยกว่าที่มีจริงมาก — วัดแล้วว่าคอขวดอยู่ที่การจัดกลุ่มงาน ไม่ใช่คำศัพท์ ดู [EXPERIMENTS.md](EXPERIMENTS.md) §7 |
